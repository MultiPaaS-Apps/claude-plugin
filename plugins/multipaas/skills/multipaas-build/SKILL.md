# Build an app on a pinned API version

The `multipaas` skill covers installing the CLI, signing in and the exit codes. The `multipaas-model` skill changes the model. The `multipaas-sign-in` skill adds end-user sign-in. This skill sets up the app's project and its calls to the generated API.

These commands need CLI 0.5.0 or later. If `multipaas --version` reports an older version, ask the user to run `brew update`, then, as a separate command, `brew upgrade multipaas`.

Creating an application (`apps create`) needs CLI 0.8.0 or later. Upgrade the same way.

`records --app-wide` needs CLI 0.10.0 or later. Upgrade the same way.

`app-identity` needs CLI 0.9.0 or later. Upgrade the same way.

`roles` and `app-identity role` need CLI 0.11.0 or later, and so does `--role` taking a role's id. Check `multipaas --version` first, and if it is older, ask the user to upgrade as above.

`envs` and `--env` need CLI 0.11.0 or later. Upgrade the same way.

## Set up the project

Run these in the app's own directory, which is where `multipaas.json` lives.

1. Find the application: `multipaas apps list --json`. If the list is `[]` or none fits, offer to create one, and on a yes run `multipaas apps create --name NAME --json`. Its `application.id` is the `APP_ID` from here on, and the new application has no app-tenant yet. If it exits 1 with `UNAUTHORIZED`, tell the user to ask a Client manager in their organization to create it or give them permission. For `CLIENT_REQUIRED`, see the `multipaas` skill. If there is still no application, stop here: the later steps need an `APP_ID`. Pick an environment to test in: `multipaas envs list --app APP_ID --json`. Each environment keeps its own app-tenants and app-wide records. Recommend a non-default environment for test data, and when only the default exists, offer to create one with `multipaas envs create --app APP_ID --name test --json`, whose `environment.id` is the `ENV_ID` from here on. It needs permission to manage the application. If it exits 1 with `UNAUTHORIZED`, tell the user to ask someone who manages the application. Find an app-tenant to test in: `multipaas tenants list --app APP_ID --env ENV_ID --json`. Ask the user which one if more than one fits. If the list is `[]`, that environment has no app-tenant yet. Offer to create one to test in, and on a yes run `multipaas tenants create --app APP_ID --env ENV_ID --name NAME --json`. It prints `{"appTenant": {"id", "name"}}`, and its `id` is the `APP_TENANT_ID` for step 2. It needs permission to manage the application. If it exits 1 with `UNAUTHORIZED`, tell the user to ask someone who manages the application.
2. `multipaas init --app APP_ID --tenant APP_TENANT_ID --json` writes `multipaas.json` and pins the newest API version. It prints:
   `{"config": {"applicationId", "testAppTenantId", "apiVersion", "oauthClientId"?}, "endpoints": {"graphql", "authorize", "token", "revoke"}}`
   Commit `multipaas.json`. Put the endpoints in the app's config. Never write a MultiPaaS host from memory.
3. `multipaas schema pull --json` writes the pinned version's schema to `multipaas.graphql` and prints `{"apiVersion", "path"}`. Point the app's GraphQL codegen at that file, and commit it with the generated code.

In this directory, `--app` defaults to the application in `multipaas.json`, and `--tenant` to its test app-tenant when `--app` is that same application. `apiVersion` is `""` when the application has no model yet. Model it first, then run `multipaas pin --json`.

## Calling the generated API

- Every request is `POST` to `endpoints.graphql`, with the headers `Authorization: Bearer <an access token>` and `X-MultiPaaS-App-Api-Version: <apiVersion from multipaas.json>`.
- There is no default version. A request without the header is refused with HTTP 400, and an unknown version with 404.
- The access token comes from end-user sign-in (see the `multipaas-sign-in` skill), or for a background job from a client-credentials request (see below). The developer's own CLI sign-in never goes into the app.
- For each entity, the schema has a query for one record by id, a paginated list, and delete and restore mutations. Create is left out when a required field without a default isn't exposed, and update is left out when none of the entity's fields are exposed. `me` is a top-level query. The schema itself is the reference: read `multipaas.graphql` rather than guessing names.
- A list takes `page: {page, pageSize}`. `page` counts from 0, and `pageSize` defaults to 20 and can be at most 100: a larger one is refused, not reduced. It returns `{items, pageInfo: {page, pageSize, hasMore}}`, with live records only, newest first. Fetch the next page while `hasMore` is true.
- A top-level list can't be filtered. To show one record's children, such as a cookbook's recipes, give the parent entity a `related` field over the child's reference field (see the `multipaas-model` skill), and query it on the parent: `cookbook(id: …) { recipes { items { … } } }`. It takes the same `page` argument. Don't fetch every record and filter in the app.
- A reference field is set through its `…Id` input. Reading it returns the record it points at, even when that record is retired, or `null` when there is none or the end user can't read it.
- The API returns only records the token's caller may read: the signed-in user, or for an app-identity token, what the identity's roles and shares allow. So the app never filters by user. On a managed entity (the default) a Member reads only the records they created (they manage them) and records shared with them; records of an unmanaged entity follow their parent record's access instead, and one with no live parent of its own app-tenant to follow can't be read even by its creator, only by roles holding `record.view_all`, `record.edit_all` or `record.manage_all` for its entity or an entity above it. A role holding `record.view_all` for an entity reads all of its records in the app-tenant. To let every member see every record, add `record.view_all` for the entity to the Member role in the MultiPaaS web app, or declare a role with `multipaas roles create --key KEY --name NAME --permission record.view_all=ENTITY_ID --json` (CLI 0.11.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade) and give it to members by invitation, or through an import's `memberships.jsonl` (see the `multipaas-import` skill), which names the role by its name. Sharing one record is done in the web app; the generated API has no sharing mutation. `createdBy` is set by MultiPaaS and grants nothing by itself. See https://multipaas.com/docs/concepts/who-can-read-which-records/.
- A refused request carries `errors[0].extensions.code`. For `VALIDATION`, `errors[0].extensions.fieldErrors` is `[{"field", "rule", "message"}]`, where `field` is the input's GraphQL name: `…Id` for a reference, `page` or `pageSize` for a list's paging, and empty when the field can't be named.
- The CLI doesn't run queries against the app's API. To see what records the app-tenant holds, use `multipaas records list` (below).
- An enum field is a GraphQL enum named for its enum type. Send and read its values by their GraphQL names, which `multipaas.graphql` lists.
- An app pinned to a version built after app-wide records shipped (its schema has an `enum RecordScope`) also gets these. Each record type has `appWide: Boolean!`. A list takes `scope: ALL | TENANT | APP_WIDE`, and the default is `ALL`: the app-tenant's own records plus the app-wide records the caller's roles let them view. `createdBy` has `kind: PERSON | APP`. A user's `account` is `null` under an app-wide token, when the user is an app identity (under any token, `me` included), and when the user is the author of an app-wide record, so never read through `account` without a null check. A version pinned before that has none of these, and the `multipaas-upgrade` skill moves the app forward.

## Background jobs that act as the app

A job that runs without an end user, such as one that fills a shared word list, signs in as an **app identity**: the app's own identity, which holds roles like a person does.

1. App identities need CLI 0.9.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as in the header. Create one: `multipaas app-identity create --name "JOB NAME" --json`. It prints `{"appIdentity": {"id", …}, "secret"}`: `appIdentity.id` is the `CLIENT_ID` and `secret` is the `CLIENT_SECRET`. The secret is shown once. Store it as a secret in the job's environment, never in the repo.
2. Give it roles. These need CLI 0.11.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as in the header. List the application's roles with `multipaas roles list --json`, and add `--tenant APP_TENANT_ID` to include that app-tenant's own roles. If none fits, see the permissions with `multipaas roles permissions --json` and declare one with `multipaas roles create --key KEY --name NAME --permission PERMISSION --json`. Repeat `--permission` for each permission, and write an entity-targeted one as `PERMISSION=ENTITY_ID`, with the entity id from `multipaas model show --json`. Then give it to the identity with `multipaas app-identity role add CLIENT_ID --role KEY --json`, which gives it at the test app-tenant. `--role` takes the role's key, or its id from `roles list` when an application role and an app-tenant role share a key and the command refuses with `AMBIGUOUS_ROLE`. Use `--tenant APP_TENANT_ID` for another app-tenant, or `--app-wide` for the whole application. `multipaas app-identity role list CLIENT_ID` lists what it holds in a scope, and `multipaas app-identity role remove CLIENT_ID --role KEY` takes one role back. Only `role list` and the web app's page for the identity show its grants, and only to someone who can manage access in that scope: `access.manage` at the app-tenant, or `access.manage.application` with `--app-wide`. For anyone else, `role list` comes back empty and `role remove` refuses with `NOT_FOUND`. An app-wide token (step 3) needs a role held across the application. An app-tenant token reads app-wide records with a role holding `record.app_wide.view` at that app-tenant or across the application, or `record.app_wide.edit` or `record.app_wide.manage` across the application. Writing app-wide records takes an app-wide token and a role held across the application with `record.app_wide.create` or `record.app_wide.edit` on the entity; given at an app-tenant, those permissions grant nothing. Reading or writing one app-tenant's data needs a role at that app-tenant or across the application.
3. Get a token: `POST` to `endpoints.token` from `multipaas init --json` with `grant_type=client_credentials`, identifying the client either by the form fields `client_id` and `client_secret` or by HTTP Basic carrying the id and secret together, not both, plus `app_tenant=APP_TENANT_ID` for one app-tenant's data, or no `app_tenant` for the application's app-wide data. The answer has `access_token` and `expires_in` (3600 seconds) and no refresh token, so ask again when it expires.

   ```
   printf 'user = "%s:%s"\n' "$CLIENT_ID" "$CLIENT_SECRET" | curl -s -K - -X POST "$TOKEN_ENDPOINT" -d grant_type=client_credentials -d app_tenant="$APP_TENANT_ID"
   ```

   That asks for one app-tenant's token. For an app-wide token, drop `-d app_tenant="$APP_TENANT_ID"`.

   In the job's own code, send the secret from its HTTP client (Basic auth or the request body), never through a shell command line.

   `invalid_target` means the identity can't act in the scope asked for. Without `app_tenant`: it holds no role across the application. With `app_tenant`: it holds no role at that app-tenant or across the application, or the id isn't an active app-tenant of this application.

   `invalid_client` (HTTP 401) means the id or secret is wrong, the secret was revoked, or the identity was retired, and the answer doesn't say which. Find out with the CLI, never by trying other secrets, and never revoke a secret or retire an identity unless the user chooses to. If `multipaas app-identity list --json` doesn't list `CLIENT_ID`, the id is wrong or the identity was retired: tell the user, and only if they agree create a new identity and give it its roles as in steps 1 and 2, since a retired identity can't come back. If it is listed, compare the secret's last four characters with `lastFour` in `multipaas app-identity secret list CLIENT_ID --json`, which lists only unrevoked secrets. When one matches, check that the job sends that whole secret exactly as it was printed and, with HTTP Basic, sends `Basic` and the base64 of `CLIENT_ID:CLIENT_SECRET`; if it still fails, treat the secret as wrong. When none matches, or the secret is wrong, add one with `multipaas app-identity secret add CLIENT_ID --json` and give it to the user to deploy. An identity holds at most two unrevoked secrets: if it already has two, ask the user which one to revoke, and revoke only that one. `invalid_request` comes back when the request sends HTTP Basic and a `client_secret` form field together: send one.
4. Call the generated API as in the section above, with that token. The scope follows the token. A tenantless token reads and writes only app-wide records, and it needs an API version built after app-wide records shipped: an older one answers `403 insufficient_scope`. An app-tenant token writes that app-tenant's records, and reads them plus the app-wide records its roles let it view.
5. Rotate the secret: `multipaas app-identity secret add CLIENT_ID --json`, deploy the new one, then revoke the old one: find its `id` in `multipaas app-identity secret list CLIENT_ID --json` (under `secrets`, told apart by `lastFour` or `createdAt`) and run `multipaas app-identity secret revoke SECRET_ID --json` with it. A revoked secret gets no new tokens, but tokens already issued with it keep working until they expire. Only when the user asks to stop the identity at once, retire it with `multipaas app-identity retire CLIENT_ID --json`: its tokens stop working immediately, and this can't be undone.

An app identity's token works only on the generated API: its records and the `me` query. It can't manage app-tenants, their members or invitations, roles or role grants, OAuth clients, app identities or the model: the CLI and the web app refuse its token, and the generated API has no such operations. When a job needs one of those, it can't do it as the app. Tell the user someone signed in to MultiPaaS has to do it.

## Moving to a newer API version

A model change mints a new API version. The app stays on its pin until it moves, so a change never breaks it. To see what changed or to move the app, use the `multipaas-upgrade` skill.

## Test data

The `records` commands read and write the test app-tenant's records, or with `--app-wide` the application's app-wide records, as the developer, with their own permissions in the web app. They go through MultiPaaS's own API, not the app's generated one, so the data is keyed by **field id** (from `multipaas model show --json`), not by field name.

| Command | Does |
|---|---|
| `multipaas records list --entity ENTITY_ID --json` | `[{"id", "appWide", "data", "createdAt", "updatedAt"}]`, newest first |
| `multipaas records get --entity ENTITY_ID --id RECORD_ID --json` | `{"record": {"id", "appWide", "data", "createdAt", "updatedAt"}}`; a record that doesn't exist is a refusal |
| `multipaas records list --entity ENTITY_ID --parent-field FIELD_ID --parent-record RECORD_ID --json` | The child records of that parent, newest first: the records whose parent reference field (`isParent` in `model show`) holds `--parent-record`. Give both flags or neither |
| `multipaas records create --entity ENTITY_ID --data '{"FIELD_ID": value}' --json` | `{"record": {...}}` |
| `multipaas records update --entity ENTITY_ID --id RECORD_ID [--data '{...}'] [--clear FIELD_ID,FIELD_ID] --json` | Sets the fields in `--data`, clears those in `--clear`, and keeps the rest |
| `multipaas records retire --entity ENTITY_ID --id RECORD_ID --json` | Retires the record |
| `multipaas records list --app-wide --entity ENTITY_ID --json` | The application's app-wide records. Add `--app-wide` to any command above, and `create`, `get`, `update` and `retire` act on app-wide records too. It replaces the default test app-tenant, and the CLI refuses it together with `--tenant`; each record carries `"appWide"` |

Without `--app-wide`, `records list` returns only the test app-tenant's own records. An app-wide record is visible to every app-tenant in its environment whose roles allow `record.app_wide.view`.

App-wide records belong to the environment the command runs in. `records --app-wide` acts in the application's default environment unless it is given `--env ENV_ID`. `records` takes `--env` only with `--app-wide`; the CLI refuses it together with `--tenant`, because a tenant already belongs to one environment. The `--env` must be one of `--app`'s environments. An app-wide token (a job's) always works in the default environment.

## When MultiPaaS refuses

A refusal exits 1 with `{"error": {"code", "message"}}`. Tell the user the message as it is.

| Code | Meaning |
|---|---|
| `NOT_INITIALIZED` | No `multipaas.json` here. Run `init` |
| `NOT_PINNED` | `multipaas.json` pins no version of this application. Run `pin` |
| `NO_API_VERSION` | The application has no model yet. Model it first |
| `NOT_FOUND` | One of the ids the refused command was given doesn't exist or isn't reachable by the user, whatever the message says (for example "no application X that you can reach", "appTenant not found"). Check each id against the list for its kind, and fix it before retrying. Application: `multipaas apps list`. API version: `multipaas versions list`. App-tenant (`--tenant`, or `testAppTenantId` in `multipaas.json`): `multipaas tenants list --app APP_ID`; if it isn't there, tell the user to ask for access. Only if the user names an app-tenant they want instead, correct `multipaas.json` to that one by running `multipaas init --app APP_ID --tenant APP_TENANT_ID --api-version API_VERSION --json` with their chosen id, taking `API_VERSION` from the `apiVersion` already in `multipaas.json` so the pin stays where it is, and leaving `--api-version` out only when that value is empty. If `init` refuses that version, tell the user, and never retry without the flag. Never pick an app-tenant yourself to get past it. Record: first check the command's `--entity` id against `multipaas model show --json`, then its record id with `multipaas records list --entity ENTITY_ID`, adding `--app-wide` if the refused command used it, because without it the list shows only app-tenant records. If the entity isn't in `model show`, follow the `ENTITY_NOT_FOUND` row below, and an empty list for it doesn't mean the record is missing. App identity (`app-identity secret add` or `list`, or any `app-identity role` command): `multipaas app-identity list`. Role (`app-identity role add --role`, `role remove --role`): `multipaas roles list --tenant APP_TENANT_ID --json` (without `--tenant` for `--app-wide`), whose key or id `--role` takes. Role grant (`app-identity role remove`): `multipaas app-identity role list CLIENT_ID` with the same `--tenant` or `--app-wide`. An empty list, or "holds no role", doesn't mean the role isn't held: no `multipaas` command shows the developer's permissions, and seeing or removing an app identity's grants needs `access.manage` at that app-tenant (`access.manage.application` with `--app-wide`). Tell the user that, and ask someone who manages access there to run the command or give them that permission. Once the user confirms they hold it, an empty list or "holds no role" means the identity really doesn't hold the role in that scope. Never retry in another scope. Secret (`app-identity secret revoke`): `multipaas app-identity secret list CLIENT_ID`, and never treat an old secret as revoked until `secret revoke` succeeds. Client (`apps create --client`): use one of the clients the `CLIENT_REQUIRED` refusal names; with no client at all ("no client you can create applications in"), tell the user to ask a Client manager in their organization to create the application or give them permission. With `records --app-wide`, `roles create` (which always asks for application access) or `app-identity role … --app-wide`, "no application-wide access" means the user holds no role across the whole application: ask someone who manages the application's access to give them application-wide access. Only for `records --app-wide`, `--tenant` is the fallback. For `roles create` and `app-identity role … --app-wide`, never move the grant to `--tenant` to get past it, because an app-tenant grant gives nothing to an app-wide token or to app-wide writes (step 2). Never retry by creating records elsewhere to get past it |
| `ENTITY_NOT_FOUND` | The `--entity` id on a `records` command isn't an entity of this application. Take the id of the entity the user meant from `multipaas model show --json` and run the command again with only that id. If `model show` no longer lists that entity, tell the user it was retired, and never write to a different entity |
| `UNAUTHORIZED` | The user lacks the permission in the web app, for example `record.create`, or the app-tenant isn't one they can reach. `roles create` needs permission to manage the application's access across the application (`access.manage.application`). All three `app-identity role` commands need `application.manage_oauth`, because they look the identity up. For `role list` and `role remove`, a missing `access.manage` shows up as an empty list or `NOT_FOUND`, not `UNAUTHORIZED`. `role add` and `role remove` also need `access.manage` at the app-tenant they act in, or `access.manage.application` with `--app-wide`. `roles create`, `app-identity role add` and `role remove` are also refused when the role carries a permission the signed-in developer doesn't hold themselves. Drop that permission from the role, or ask someone who holds it to run the command, and never widen the developer's own access to get past it without asking the user |
| `AMBIGUOUS_ROLE` | `--role` names a key that an application role and an app-tenant role both have. The refusal names both ids with their scopes. Take the id of the role the user meant from it, or from `multipaas roles list --tenant APP_TENANT_ID --json`, where `appTenant` is `null` for the application role, and run the command again with `--role` set to that id |
| `VALIDATION` | A record's data breaks the model. The message names the fields |
| `CLI_ERROR` | A bad flag, for example `--data` that isn't JSON, or `--app` missing outside a directory with `multipaas.json`. Fix it and run the command again |
