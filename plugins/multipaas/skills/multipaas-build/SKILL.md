# Build an app on a pinned API version

The `multipaas` skill covers installing the CLI, signing in and the exit codes. The `multipaas-model` skill changes the model. The `multipaas-sign-in` skill adds end-user sign-in. This skill sets up the app's project and its calls to the generated API.

These commands need CLI 0.5.0 or later. If `multipaas --version` reports an older version, ask the user to run `brew update`, then, as a separate command, `brew upgrade multipaas`.

Creating an application (`apps create`) needs CLI 0.8.0 or later. Upgrade the same way.

`records --app-wide` needs CLI 0.10.0 or later. Upgrade the same way.

`app-identity` needs CLI 0.9.0 or later. Upgrade the same way.

`roles` and `app-identity role` need CLI 0.11.0 or later, and so does `--role` taking a role's id. Check `multipaas --version` first, and if it is older, ask the user to upgrade as above.

`roles update` needs CLI 1.1.0 or later. Upgrade the same way.

`envs` and `--env` need CLI 0.13.0 or later. Upgrade the same way.

`records list --where`, `--order-by` and `--count` need CLI 1.1.0 or later. Upgrade the same way.

`records update --expected-version`, and `version` in the output of `records get`, `list`, `create` and `update`, need CLI 1.4.0 or later; `files` in that output needs 1.3.0 or later. Upgrade the same way.

## Set up the project

Run these in the app's own directory, which is where `multipaas.json` lives.

1. Find the application: `multipaas apps list --json`. If the list is `[]` or none fits, offer to create one, and on a yes run `multipaas apps create --name NAME --json`. Its `application.id` is the `APP_ID` from here on, and the new application has no app-tenant yet. If it exits 1 with `UNAUTHORIZED`, tell the user to ask a Client manager in their organization to create it or give them permission. For `CLIENT_REQUIRED`, see the `multipaas` skill. If there is still no application, stop here: the later steps need an `APP_ID`. Pick an environment to test in: `multipaas envs list --app APP_ID --json`. Each environment keeps its own app-tenants and app-wide records. Recommend a non-default environment for test data, and when only the default exists, offer to create one with `multipaas envs create --app APP_ID --name test --json`, whose `environment.id` is the `ENV_ID` from here on. It needs permission to manage the application. If it exits 1 with `UNAUTHORIZED`, tell the user to ask someone who manages the application. Find an app-tenant to test in: `multipaas tenants list --app APP_ID --env ENV_ID --json`. Ask the user which one if more than one fits. If the list is `[]`, there is no app-tenant in that environment that you can reach. Offer to create one to test in, and on a yes run `multipaas tenants create --app APP_ID --env ENV_ID --name NAME --json`. It prints `{"appTenant": {"id", "name"}}`, and its `id` is the `APP_TENANT_ID` for step 2. It needs permission to manage the application. If it exits 1 with `UNAUTHORIZED`, tell the user to ask someone who manages the application.
2. `multipaas init --app APP_ID --env ENV_ID --tenant APP_TENANT_ID --json` writes `multipaas.json` and pins the newest API version. With `--env ENV_ID`, only that environment's app-tenants can be chosen. Leave it out only when the app-tenant is in the default environment or one you hold a role at directly, whatever environment it is in. From CLI 1.2.0, `init` saves the app-tenant's environment in `multipaas.json` as `environmentId`, the environment the app signs in to (see the `multipaas-sign-in` skill), with or without `--env`; an older CLI saves none. It prints:
   `{"config": {"applicationId", "testAppTenantId", "environmentId"?, "apiVersion", "oauthClientId"?}, "endpoints": {"graphql", "authorize", "token", "revoke"}}`
   Commit `multipaas.json`. Put the endpoints in the app's config. Never write a MultiPaaS host from memory.
3. `multipaas schema pull --json` writes the pinned version's schema to `multipaas.graphql` and prints `{"apiVersion", "path"}`. Point the app's GraphQL codegen at that file, and commit it with the generated code.

In this directory, `--app` defaults to the application in `multipaas.json`, and `--tenant` to its test app-tenant when `--app` is that same application. From CLI 1.2.0, `--env` defaults to its `environmentId` the same way, for `app-identity`, `import` and `tenants create`, and for `records` and `app-identity role` with `--app-wide`. `apiVersion` is `""` when the application has no model yet. Model it first, then run `multipaas pin --json`.

## Calling the generated API

- Every request is `POST` to `endpoints.graphql`, with the query and its variables as a JSON body and the headers `Content-Type: application/json`, `Authorization: Bearer <an access token>` and `X-MultiPaaS-App-Api-Version: <apiVersion from multipaas.json>`.
- There is no default version. A request without the header is refused with HTTP 400, and an unknown version with 404.
- The access token comes from end-user sign-in (see the `multipaas-sign-in` skill), or for a background job from a client-credentials request (see below). The developer's own CLI sign-in never goes into the app.
- For each entity, the schema has a query for one record by id, a paginated list, and delete and restore mutations. Create is left out when a required field without a default isn't exposed, and update is left out when none of the entity's fields are exposed. `me` is a top-level query. The schema itself is the reference: read `multipaas.graphql` rather than guessing names.
- A list takes `page: {page, pageSize}`. `page` counts from 0, and `pageSize` defaults to 20 and can be at most 100: a larger one is refused, not reduced. It returns `{items, pageInfo: {page, pageSize, hasMore}}`, with live records only. An app pinned to a version whose `PageInfo` has `nextCursor` walks a list by cursor: pass each page's `nextCursor` back as `cursor`, with `page.page` 0 and the same `orderBy`, until `hasMore` is false. `recordHistory` takes no `cursor` and its `nextCursor` is always null: page it by number while `hasMore` is true. Such a list is ordered by its `orderBy` field with records with no value last, then newest first, then by record id. With no `orderBy` it is newest first, then by record id. A record is in the list while it exists, the caller can read it, and it meets the list's arguments: its `where`, a top-level list's `scope`, and, in a related list, pointing at the parent record. Each page lists, in the list's order, the first `pageSize` of the records that are in the list when that page is read and sort after the walk's position. The first page, read without a cursor, starts at the beginning of the list. After that, the position is the place the previous page's last record held when that page was read, and it stays there whatever later happens to that record. So a cursor walk lists each record that is in the list for the whole walk exactly once, unless its `orderBy` field changes mid-walk: it then moves to its new place, so the walk can miss it or list it twice. Ordered by `UPDATED_AT`, any change to a record moves it. A record that is in the list for only part of the walk is listed if it is in the list when the walk reaches its place. With no `orderBy`, a record's place is its creation time, which updates, restores and imports keep, and a newly created record is normally newer than anything the walk has reached, so it is normally not listed. Use page numbers only to jump to a page. A cursor from another `orderBy`, a malformed one, or one with `page.page` above 0 is refused with `VALIDATION`. On a version without `nextCursor`, fetch the next page while `hasMore` is true.
- To show one record's children, such as a cookbook's recipes, give the parent entity a `related` field over the child's reference field (see the `multipaas-model` skill), and query it on the parent: `cookbook(id: …) { recipes { items { … } } }`. It takes the same `page` argument.
- An app pinned to a version whose schema has `input StringFilter` can filter, order and count every entity list, top-level and related. `where: {<field>: {<operator>: value}}` keeps records matching every condition: `eq` on every field except related, file and list fields, which take no scalar condition (a related field takes `some` and `none`, below; a list field takes only `has` and `isNull`, in the list bullet below; a file field can't be filtered); `isNull` on the same fields and on list fields, except `id`; `in` on text, enums, references and `id`; `notIn` on enums, references and `id`; `lt`, `lte`, `gt` and `gte` on numbers and timestamps; and `contains`, `startsWith` and `endsWith` on text (case-insensitive); `in`, `notIn`, `contains`, `startsWith` and `endsWith` don't apply to list fields. A reference is filtered by the id it holds, and a reference to a record the caller can't read counts as no value, as it reads `null`: `isNull: true` matches it, `eq` and `in` don't, and `notIn` does. An app pinned to a version whose `…ReferenceFilter` inputs have an `is` field can also keep records by their related and referenced records: a related field takes `some: {…}` (at least one related record meets the conditions) or `none: {…}` (none does), and a reference takes `is: {…}` (the record it points at meets them), each holding the other entity's filter, so `words(where: {cards: {none: {}}})` lists the words with no card. They nest at most 3 levels, each `where` holds at most 100 conditions in all, counting nested ones and each `some`, `none` and `is`, and a related or referenced record the caller can't read counts as absent: `none` matches, `some` and `is` don't. A null `some`, `none` or `is` is refused: use `{}` for any record, or `isNull` to test the reference itself. `orderBy: {field: FIELD_NAME, direction: ASC | DESC}` sorts by one of the record's own fields (not a reference), records with no value last; with no `orderBy` a list is newest first. `totalCount` on the page counts every match, and a query selecting only `totalCount` fetches no records, so use it for badges. Read the exact input names from `multipaas.graphql`. Never fetch every page to filter, sort or count in the app. A version without `StringFilter` has none of these, and the `multipaas-upgrade` skill moves the app forward.
- A list field appears on its record type as `[String!]`, or `[<Enum>!]` for an enum list (with a trailing `!` when the field is not null), and its filter input is `StringListFilter` or `<Enum>ListFilter`. It is read and written as an array and filtered with `has: VALUE` (an exact match on one element, case-sensitive) and `isNull`. A list field is never in `orderBy`. Writing a list replaces the whole list; `[]` is an empty list, and `null` clears it, unless the field is required or not null, which refuse null. If `multipaas model show` lists a list field but the pinned schema has no field of that name, the pinned API version predates that field or its current name: use the `multipaas-upgrade` skill.
- An app pinned to a version whose record types have `version: ID!` can update safely when two requests may change the same record, such as a counter that enforces a daily limit. Read the record with its `version` and `deletedAt`, work out the change, and send `update<Entity>(input: {id, expectedVersion: <the version read>, …})`. If the record changed since that read, the update writes nothing and is refused with `errors[0].extensions.code` `CONFLICT`: read it again with the same fields, work out the change again from the record it returns, and retry, a few times at most, stopping when the new data makes the change wrong (the limit is reached). The record is gone when a read returns it with `deletedAt` set (it was retired) or returns `null` (the caller can no longer read it). Through the CLI, `records get` refuses with `NOT_FOUND` in both cases. An update refused with `NOT_FOUND` means the record was already retired, the caller can't read it, or the caller can read it but may not change it: read it again, and when the read returns it with `deletedAt` unset, tell the user they may not change it. A record the caller can't read is never refused with `CONFLICT`. Whenever it is gone, or the update is refused with `NOT_FOUND`, stop and tell the user, never recreate it or write the change somewhere else. Every update changes `version`, the update's result carries the new one, and `recordHistory`'s ids are the same ids. A restore returns nothing, so read the record after it for its version. Without `expectedVersion` an update writes what it's given, even over a change it never saw. A version without `version` has none of this, and the `multipaas-upgrade` skill moves the app forward.
- A reference field is set through its `…Id` input. Reading it returns the record it points at, even when that record is retired, or `null` when there is none or the end user can't read it.
- An app pinned to a version whose schema has a `type File` with a `urlExpiresAt` field and no `createdAt` can keep a file on a record (an older version can have `type File` only as an entity's record type, which always has `createdAt`), in a `file` field (see the `multipaas-model` skill). The app uploads in three steps, from its server or from the end user's browser: the generated API and file storage accept every origin, so a browser needs no proxy. (1) `request<Entity>FileUpload(input: {field, filename, contentType, sizeBytes, sha256})` takes the file field's enum value, the file's name and content type (each 1 to 255 characters), its size in bytes (a whole number, at least 1, within the field's maximum, which is 512 MiB unless the field sets less) and its SHA-256 as 64 lowercase hex digits, and returns `{fileId, url, headers, expiresAt}`, where `headers` is a list of `{name, value}`; the caller needs `record.create` or `record.edit_all` on the entity, or for an app-wide record `record.app_wide.create` or `record.app_wide.edit`, so editing a record only through a share or as its manager isn't enough. (2) The app PUTs the bytes to `url` within 15 minutes, sending each returned `{name, value}` as one request header, exactly as given; storage refuses a body whose size or hash differs, and if it refuses the PUT or the 15 minutes pass, the app requests a new upload with `request<Entity>FileUpload` and PUTs again. (3) The app passes `fileId` as `<field>FileId` when it creates or updates the record. That write is refused, with an error naming the field, if the file doesn't exist or was requested by another user (both read "does not exist"), isn't uploaded yet, is over the field's maximum, or is already on another record or field. A refused write changes nothing and binds no file, so the app keeps the rest of the record input and retries. If the file isn't uploaded yet, finish the PUT and retry with the same `fileId`. If the file doesn't exist, another user requested it or it is already on another record or field, request a new upload, PUT it and retry with the new `fileId`. If the file is over the field's maximum, upload a smaller file under a new `fileId`, or raise the maximum with `multipaas field update --app APP_ID --id FIELD_ID --max-file-bytes BYTES --json` and retry with the same `fileId`. That flag needs CLI 1.1.0 or later: check `multipaas --version`, and if it is older, ask the user to upgrade as above. Make the request and the record write as the same user, since only the user who requested an upload can bind it. So a file a user uploads from the browser can't be bound with an app-identity token, and one a job uploads as an app identity can't be bound with a user's token. A token refreshed for that user works, and the PUT sends only the returned headers, never an access token. In the browser, hash with `crypto.subtle.digest("SHA-256", await file.arrayBuffer())` and write it as lowercase hex. `crypto.subtle` exists only in a secure context, HTTPS or `localhost`. Web Crypto has no incremental digest, so for a file too large to hold in memory, hash it in chunks with an incremental SHA-256 implementation. Send `file.type`, or `application/octet-stream` when the browser leaves it empty. Send the `File` itself as the PUT body. `clear: [<FIELD>]` removes the file from a record, but only from a file field that isn't required: on a required one it is refused, so replace the file instead. Reading the field, `photo { filename contentType sizeBytes url urlExpiresAt }`, returns a link that is fresh on every read and works for 15 minutes, so ask for it when showing the file rather than storing it, and treat it as a secret, since anyone holding it can fetch the file until it expires. A record the caller can't read returns no link, so read the record with the end user's own access token when showing it to that user: a read with an app-identity token doesn't check the user. The link shows images (except SVG), audio, video and PDF in place and downloads everything else. A record's history returns the file each earlier version had. Replacing or clearing a file keeps the old one in that history, and retiring or restoring a record leaves its files as they are. An upload no record holds may be removed a day after it was requested, so bind it soon after the PUT. A file field can't be filtered or ordered by, and an import can carry files (see the `multipaas-import` skill). A version whose schema has no such `type File` has no file fields, and the `multipaas-upgrade` skill moves the app forward.
- The API returns only records the token's caller may read: the signed-in user, or for an app-identity token, what the identity's roles and shares allow. So the app never filters by user. On a managed entity (the default) a Member reads only the records they created (they manage them) and records shared with them; records of an unmanaged entity follow their parent record's access instead, and one with no live parent of its own app-tenant to follow can't be read even by its creator, only by roles holding `record.view_all`, `record.edit_all` or `record.manage_all` for its entity or an entity above it. A role holding `record.view_all` for an entity reads all of its records in the app-tenant. To let every member see every record, add `record.view_all` for the entity to the Member role with `multipaas roles update --role member --add-permission record.view_all=ENTITY_ID --json` (CLI 1.1.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade), or declare a role with `multipaas roles create --key KEY --name NAME --permission record.view_all=ENTITY_ID --json` (CLI 0.11.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade) and give it to members by invitation, or through an import's `memberships.jsonl` (see the `multipaas-import` skill), which names the role by its name. Sharing one record is done in the web app; the generated API has no sharing mutation. `createdBy` is set by MultiPaaS and grants nothing by itself. See https://multipaas.com/docs/concepts/who-can-read-which-records/.
- A refused request carries `errors[0].extensions.code`. For `VALIDATION`, `errors[0].extensions.fieldErrors` is `[{"field", "rule", "message"}]`, where `field` is the input's GraphQL name: `…Id` for a reference, `page` or `pageSize` for a list's paging, and empty when the field can't be named. A `unique` entry also carries `constraint`, the id of the unique constraint the write broke (`model show` lists them). When a write breaks two constraints, both appear.
- The CLI doesn't run queries against the app's API. To see what records the app-tenant holds, use `multipaas records list` (below).
- An enum field is a GraphQL enum named for its enum type. Send and read its values by their GraphQL names, which `multipaas.graphql` lists.
- An app pinned to a version built after app-wide records shipped (its schema has an `enum RecordScope`) also gets these. Each record type has `appWide: Boolean!`. A list takes `scope: ALL | TENANT | APP_WIDE`, and the default is `ALL`: the app-tenant's own records plus the app-wide records in its environment that the caller's roles let them view. `createdBy` has `kind: PERSON | APP`. A user's `account` is `null` under an app-wide token, when the user is an app identity (under any token, `me` included), and when the user is the author of an app-wide record, so never read through `account` without a null check. A version pinned before that has none of these, and the `multipaas-upgrade` skill moves the app forward.

## Background jobs that act as the app

A job that runs without an end user, such as one that fills a shared word list, signs in as an **app identity**: the app's own identity, which holds roles like a person does.

1. App identities need CLI 0.9.0 or later, and CLI 1.2.0 or later when the identity belongs outside the default environment, which includes a project whose test app-tenant is outside it (on CLI 1.2.0 the identity defaults to `environmentId` in `multipaas.json`, and an older CLI creates it in the default environment): check `multipaas --version` first, and if it is older than what the job needs, ask the user to upgrade as in the header. Upgrading adds no `environmentId` to a `multipaas.json` an older `init` wrote, so without `--env` the `app-identity` commands, and the `role` commands with `--app-wide`, use the default environment. To use another, run `init` again as the `init` step in "Set up the project" describes, adding `--api-version API_VERSION` with the file's `apiVersion` to keep the pin (a bare `init` pins the newest version), or pass `--env ENV_ID` on those commands. Create one: `multipaas app-identity create --name "JOB NAME" --json`. An identity belongs to the environment it is created in. `--env` on `app-identity` and `app-identity role`, and its default from `environmentId`, need CLI 1.2.0 or later; if the CLI is older, ask the user to upgrade as in the header. `--env ENV_ID` names it, and without `--env` it is `environmentId` in `multipaas.json` when that file is for the same application, else the default environment. Every later `app-identity` command other than the `role` commands takes the same `--env` and finds only that environment's identities; the `role` commands take `--env` only with `--app-wide` (step 2). It prints `{"appIdentity": {"id", …}, "secret"}`: `appIdentity.id` is the `CLIENT_ID` and `secret` is the `CLIENT_SECRET`. The secret is shown once. Store it as a secret in the job's environment, never in the repo.
2. Give it roles. These need CLI 0.11.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as in the header. List the application's roles with `multipaas roles list --json`, and add `--tenant APP_TENANT_ID` to include that app-tenant's own roles. If none fits, see the permissions with `multipaas roles permissions --json` and declare one with `multipaas roles create --key KEY --name NAME --permission PERMISSION --json`. Repeat `--permission` for each permission, and write an entity-targeted one as `PERMISSION=ENTITY_ID`, with the entity id from `multipaas model show --json`. To change a role that already exists, such as the Member role, run `multipaas roles update --role KEY --add-permission PERMISSION --remove-permission PERMISSION --json`. Repeat either flag. `--remove-permission` takes a permission as `roles list` shows it, and is refused with `NOT_FOUND` when the role doesn't carry it. It changes application roles only and needs CLI 1.1.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade. Then give it to the identity with `multipaas app-identity role add CLIENT_ID --role KEY --json`, which gives it at the test app-tenant. That works only when the test app-tenant is in the identity's environment; otherwise add `--tenant APP_TENANT_ID` for an app-tenant of that environment, or `--app-wide --env ENV_ID`. `--role` takes the role's key, or its id from `roles list` when an application role and an app-tenant role share a key and the command refuses with `AMBIGUOUS_ROLE`. Use `--tenant APP_TENANT_ID` for another app-tenant, or `--app-wide` for the whole application. A role given across the application counts in the environment it was given in, and an identity holds roles only in its own environment: `--app-wide --env ENV_ID` gives it in that environment (this and the default need CLI 1.2.0 or later; without `--env`, `environmentId` in `multipaas.json` when that file is for the same application, else the default environment), and the web app gives it in the environment picked there. An identity can't be given a role in another environment, and `--tenant` takes an app-tenant of the identity's own environment. `--env` can't be combined with `--tenant`, and needs `--app-wide`. `multipaas app-identity role list CLIENT_ID --json` lists what it holds in a scope, and `multipaas app-identity role remove CLIENT_ID --role KEY --json` takes one role back. Both default to the test app-tenant, like `role add`, and for an identity outside that app-tenant's environment they refuse with `NOT_FOUND` "no app identity": pass `--tenant APP_TENANT_ID` of an app-tenant in the identity's environment, or `--app-wide --env ENV_ID`. Only `role list` and the web app's page for the identity show its grants, and only to someone who can manage access in that scope: `access.manage` at the app-tenant, or `access.manage.application` with `--app-wide`, which the CLI checks in the environment the command acts in (see `--env` above). For anyone else, `role list` comes back empty and `role remove` refuses with `NOT_FOUND`. An app-wide token (step 3) works in the identity's own environment and needs a role held across the application there. An app-tenant token reads app-wide records with a role holding `record.app_wide.view` at that app-tenant or across the application in its environment, or `record.app_wide.edit` or `record.app_wide.manage` across the application in its environment. Writing app-wide records takes an app-wide token and a role held across the application in the identity's environment with `record.app_wide.create` or `record.app_wide.edit` on the entity; given at an app-tenant, those permissions grant nothing. Reading or writing one app-tenant's data needs a role at that app-tenant, or across the application in the app-tenant's own environment, which is the identity's environment: an identity gets no token for an app-tenant of another environment.
3. Get a token: `POST` to `endpoints.token` from `multipaas init --json` with `grant_type=client_credentials`, identifying the client either by the form fields `client_id` and `client_secret` or by HTTP Basic carrying the id and secret together, not both, plus `app_tenant=APP_TENANT_ID` for one app-tenant's data, or no `app_tenant` for its environment's app-wide data. Either way, the token is for the identity's own environment. The answer has `access_token` and `expires_in` (3600 seconds) and no refresh token, so ask again when it expires.

   ```
   printf 'user = "%s:%s"\n' "$CLIENT_ID" "$CLIENT_SECRET" | curl -s -K - -X POST "$TOKEN_ENDPOINT" -d grant_type=client_credentials -d app_tenant="$APP_TENANT_ID"
   ```

   That asks for one app-tenant's token. For an app-wide token, drop `-d app_tenant="$APP_TENANT_ID"`.

   In the job's own code, send the secret from its HTTP client (Basic auth or the request body), never through a shell command line.

   `invalid_target` means the identity can't act in the scope asked for. Without `app_tenant`: it holds no role across the application in its own environment. With `app_tenant`: it holds no role at that app-tenant or across the application in its environment, the app-tenant is in another environment, or the id isn't an active app-tenant of this application. It also comes back while the identity's environment is removed but not yet erased; after the erase it is `invalid_client`. If `multipaas envs list --app APP_ID --json` no longer lists the environment, treat it as that `invalid_client` case below.

   `invalid_client` (HTTP 401) means the id or secret is wrong, the secret was revoked, the identity was retired, or its environment was removed and erased, and the answer doesn't say which. Find out with the CLI, never by trying other secrets, and never revoke a secret or retire an identity unless the user chooses to. If `multipaas app-identity list --json` doesn't list `CLIENT_ID`, look in the application's other environments too, since the list covers one environment (`--env`, else `environmentId` in `multipaas.json`, else the default): run it with `--env ENV_ID` for each environment from `multipaas envs list --app APP_ID --json`. A list that is refused (`UNAUTHORIZED`, because the developer lacks `application.manage_oauth` in that environment) hasn't looked at all: handle that refusal as the `UNAUTHORIZED` row says, and don't count that environment as having no such identity. Only when every environment's list ran and none has it, the id is wrong, the identity was retired, or its environment was removed and erased (check with `multipaas envs list --app APP_ID --json`): tell the user, and only if they agree create a new identity in a live environment and give it its roles as in steps 1 and 2, since a retired or erased identity can't come back. If it is listed, use the `--env ENV_ID` of the environment that listed it on every later command for it, here and in step 5. Compare the secret's last four characters with `lastFour` in `multipaas app-identity secret list CLIENT_ID --env ENV_ID --json`, which lists only unrevoked secrets. When one matches, check that the job sends that whole secret exactly as it was printed and, with HTTP Basic, sends `Basic` and the base64 of `CLIENT_ID:CLIENT_SECRET`; if it still fails, treat the secret as wrong. When none matches, or the secret is wrong, add one with `multipaas app-identity secret add CLIENT_ID --env ENV_ID --json` and give it to the user to deploy. An identity holds at most two unrevoked secrets: if it already has two, ask the user which one to revoke, and revoke only that one. `invalid_request` comes back when the request sends HTTP Basic and a `client_secret` form field together: send one.
4. Call the generated API as in the section above, with that token. The scope follows the token. A tenantless token reads and writes only its environment's app-wide records, as its roles allow, and it needs an API version built after app-wide records shipped: an older one answers `403 insufficient_scope`. An app-tenant token writes that app-tenant's records as its roles allow, and reads them plus the app-wide records in its app-tenant's environment that its roles let it view.
5. Rotate the secret. Every `app-identity` command here finds the identity only in its own environment, so pass its `--env ENV_ID` on each unless `multipaas.json` names that environment. First add a secret with `multipaas app-identity secret add CLIENT_ID --env ENV_ID --json`, then deploy the new one, then revoke the old one: find its `id` in `multipaas app-identity secret list CLIENT_ID --env ENV_ID --json` (under `secrets`, told apart by `lastFour` or `createdAt`) and run `multipaas app-identity secret revoke SECRET_ID --env ENV_ID --json` with it. A revoked secret gets no new tokens, but tokens already issued with it keep working until they expire. Only when the user asks to stop the identity at once, retire it with `multipaas app-identity retire CLIENT_ID --env ENV_ID --json`: its tokens stop working immediately, and this can't be undone.

An app identity's token works only on the generated API: its records and the `me` query. It can't manage app-tenants, their members or invitations, roles or role grants, OAuth clients, app identities or the model: the CLI and the web app refuse its token, and the generated API has no such operations. When a job needs one of those, it can't do it as the app. Tell the user someone signed in to MultiPaaS has to do it.

## Moving to a newer API version

A model change mints a new API version. A model with an entity or enum whose type name is `File`, `FileUpload` or `HttpHeader` gets no new version while it has one (see the `multipaas-model` skill). The app stays on its pin until it moves, so a change never breaks it. To see what changed or to move the app, use the `multipaas-upgrade` skill.

## Test data

The `records` commands read and write the test app-tenant's records, or with `--app-wide` the application's app-wide records, as the developer, with their own permissions in the web app. They go through MultiPaaS's own API, not the app's generated one, so the data is keyed by **field id** (from `multipaas model show --json`), not by field name.

| Command | Does |
|---|---|
| `multipaas records list --entity ENTITY_ID --json` | `[{"id", "appWide", "data", "createdAt", "updatedAt", "version", "files"}]`, newest first |
| `multipaas records list --entity ENTITY_ID --where '{"FIELD_ID": {"lte": 5}}' --order-by FIELD_ID:desc --json` | (CLI 1.1.0 or later) The records meeting every condition in `--where`, in that order. `--order-by` takes `createdAt`, `updatedAt` or a field id, ascending unless it ends `:desc`; a reference, related, file or list field, or an enum field whose enum no longer exists, is refused with a `VALIDATION` error naming it. Without it the list is newest first |
| `multipaas records list --entity ENTITY_ID [--where '{...}'] --count --json` | (CLI 1.1.0 or later) `{"count": N}`: how many records match, without listing them. The CLI refuses it together with `--order-by` |
| `multipaas records get --entity ENTITY_ID --id RECORD_ID --json` | `{"record": {"id", "appWide", "data", "createdAt", "updatedAt", "version", "files"}}`; a record that doesn't exist is a refusal |
| `multipaas records list --entity ENTITY_ID --parent-field FIELD_ID --parent-record RECORD_ID --json` | The child records of that parent, newest first: the records whose parent reference field (`isParent` in `model show`) holds `--parent-record`. Give both flags or neither |
| `multipaas records create --entity ENTITY_ID --data '{"FIELD_ID": value}' --json` | `{"record": {...}}` |
| `multipaas records update --entity ENTITY_ID --id RECORD_ID [--data '{...}'] [--clear FIELD_ID,FIELD_ID] [--expected-version VERSION] --json` | Sets the fields in `--data`, clears those in `--clear`, and keeps the rest. With `--expected-version` (CLI 1.4.0 or later), only if the record is still at that version, its `version` from `records get` or `list`; otherwise it's refused with `CONFLICT` and nothing is written. Pass `--expected-version` whenever the new values come from what you read, such as a count you add to or a list you append to; without it the update writes over any change made since your read to the fields it sets or clears |
| `multipaas records retire --entity ENTITY_ID --id RECORD_ID --json` | Retires the record |
| `multipaas records list --app-wide [--env ENV_ID] --entity ENTITY_ID --json` | The application's app-wide records. Add `--app-wide` to any command above, and `create`, `get`, `update` and `retire` act on app-wide records too. It replaces the default test app-tenant, and the CLI refuses it together with `--tenant`; each record carries `"appWide"` |

`--where` is a JSON object keyed by field id, or `id`, `createdAt` or `updatedAt`, each holding operators: the same conditions the app's generated API takes. Text takes `eq`, `in`, `contains`, `startsWith`, `endsWith` and `isNull`. Numbers and timestamps take `eq`, `lt`, `lte`, `gt`, `gte` and `isNull`. Booleans take `eq` and `isNull`. Enums and references take `eq`, `in`, `notIn` and `isNull`, and `id` takes `eq`, `in` and `notIn`. Values take the field's type: text and enum values are strings (an enum value must be one of the enum's values), numbers are numbers, booleans are true or false, timestamps are ISO 8601 strings, and references and `id` take record ids; `in` and `notIn` take a list, and `isNull` takes true or false. A related field takes `some` or `none`, and a reference also takes `is`, each holding a `--where` object keyed by the other entity's field ids, like `'{"RELATED_FIELD_ID": {"none": {}}}'`. `contains`, `startsWith` and `endsWith` ignore case. A list field takes `has` and `isNull`. A wrong field, operator or value is refused with a `VALIDATION` error naming the field.

Without `--app-wide`, `records list` returns only the test app-tenant's own records. An app-wide record is visible to every app-tenant in its environment whose roles allow `record.app_wide.view`.

App-wide records belong to the environment the command runs in. `records --app-wide` acts in the application's default environment unless it is given `--env ENV_ID`, or, from CLI 1.2.0, `multipaas.json` has an `environmentId` for the same application. `records` takes `--env` only with `--app-wide`; the CLI refuses it together with `--tenant`, because a tenant already belongs to one environment. The `--env` must be one of `--app`'s environments. An app-wide token (a job's) works in its identity's environment.

## When MultiPaaS refuses

A refusal exits 1 with `{"error": {"code", "message"}}`. Tell the user the message as it is.

| Code | Meaning |
|---|---|
| `NOT_INITIALIZED` | No `multipaas.json` here. Run `init` |
| `NOT_PINNED` | `multipaas.json` pins no version of this application. Run `pin` |
| `NO_API_VERSION` | The application has no model yet. Model it first |
| `NOT_FOUND` | One of the ids the refused command was given doesn't exist or isn't reachable by the user, whatever the message says (for example "no application X that you can reach", "appTenant not found"). Check each id against the list for its kind, and fix it before retrying. Application: `multipaas apps list --json`. API version: `multipaas versions list --app APP_ID --json`. Environment (`--env`, or `environmentId` in `multipaas.json`): a removed environment is gone for good and the CLI refuses it with `NOT_FOUND`, as it does an id that was never one of the application's, because it is no longer in `envs list`. The app's own API calls with a token from that environment get HTTP 401, a refresh of such a token gets `invalid_grant`, and a client-credentials request for one of its app identities gets `invalid_target`, then `invalid_client` for good once the erase has run, so get a token from a live environment (for a job, a new app identity there). List the live ones with `multipaas envs list --app APP_ID --json` and ask the user which to use. For a `multipaas.json` that names a removed environment, find an app-tenant to test in from the live environment the user chose, with `multipaas tenants list --app APP_ID --env ENV_ID --json` and that environment's `ENV_ID` (if it is `[]`, offer to create one as step 1 of "Set up the project" does), then run the `init` correction below with that `ENV_ID` and app-tenant, keeping `apiVersion` as it describes. App-tenant (`--tenant`, or `testAppTenantId` in `multipaas.json`): `multipaas tenants list --app APP_ID --json`, which lists the default environment's app-tenants and any you hold a role at directly, whatever environment it is in. If the id isn't there, look in the other environments with `multipaas tenants list --app APP_ID --env ENV_ID --json`, which lists only that environment's app-tenants: use the environment from setup when you know it, otherwise check each non-default environment from `multipaas envs list --app APP_ID --json`. Tell the user to ask for access only when no list has the id. An app-tenant of a removed environment drops out of every list for a user whose access is at that app-tenant. If `envs list` also exits with `NOT_FOUND`, the user's access to this application doesn't include a live environment: tell the user to ask someone who manages the application for access to an app-tenant in one. If `envs list` works, take an `ENV_ID` from it and use a live app-tenant from `tenants list --env ENV_ID`. If that app-tenant list is `[]`, offer to create an app-tenant in that environment, as step 1 of "Set up the project" does. Only if the user names an app-tenant they want instead, correct `multipaas.json` to that one by running `multipaas init --app APP_ID --env ENV_ID --tenant APP_TENANT_ID --api-version API_VERSION --json` with their chosen id (pass `--env ENV_ID` for the environment whose list held that id, and leave it out only when the list without `--env` held it), taking `API_VERSION` from the `apiVersion` already in `multipaas.json` so the pin stays where it is, and leaving `--api-version` out only when that value is empty. If `init` refuses that version, tell the user, and never retry without the flag. Never pick an app-tenant yourself to get past it. Record: first check the command's `--entity` id against `multipaas model show --app APP_ID --json`, then its record id with `multipaas records list --app APP_ID --entity ENTITY_ID --json`, with the same scope the refused command used: its `--tenant APP_TENANT_ID`, or its `--app-wide`, with its `--env ENV_ID` if it had one. Without them the list looks somewhere else, in the test app-tenant from `multipaas.json` or, for app-wide records, in the environment `--env` would default to: `environmentId` in `multipaas.json` when that file is for the same application (CLI 1.2.0 or later), else the default environment. If the entity isn't in `model show`, follow the `ENTITY_NOT_FOUND` row below, and an empty list for it doesn't mean the record is missing. App identity (`app-identity secret add` or `list`, or any `app-identity role` command): `multipaas app-identity list --app APP_ID --json`, with the command's `--env ENV_ID` if it had one: an identity is listed only in its own environment, so look in the others with `multipaas envs list --app APP_ID --json`. Role (`roles update --role`, `app-identity role add --role`, `role remove --role`): `multipaas roles list --app APP_ID --tenant APP_TENANT_ID --json` (without `--tenant` for `--app-wide`), whose key or id `--role` takes. For `roles update`, run that list without `--tenant`: only roles whose `appTenant` is null count. A `roles update` refused with "doesn't carry" names a `--remove-permission` the role doesn't hold: compare it with the role's permissions in `roles list`. Role grant (`app-identity role remove`): `multipaas app-identity role list CLIENT_ID --app APP_ID --json` with the same `--tenant` or `--app-wide` (and `--env ENV_ID`). An empty list, or "holds no role", doesn't mean the role isn't held: no `multipaas` command shows the developer's permissions, and seeing or removing an app identity's grants needs `access.manage` at that app-tenant (`access.manage.application` with `--app-wide`, held in the environment the command acts in). Tell the user that, and ask someone who manages access there to run the command or give them that permission. Once the user confirms they hold it, an empty list or "holds no role" means the identity really doesn't hold the role in that scope. Never retry in another scope. Secret (`app-identity secret revoke`): `multipaas app-identity secret list CLIENT_ID --app APP_ID --json`, with the command's `--env ENV_ID` if it had one, found in another environment the way the App identity lookup says, and never treat an old secret as revoked until `secret revoke` succeeds. Client (`apps create --client`): use one of the clients the `CLIENT_REQUIRED` refusal names; with no client at all ("no client you can create applications in"), tell the user to ask a Client manager in their organization to create the application or give them permission. With `records --app-wide`, `roles create` or `roles update` (which always ask for application access) or `app-identity role … --app-wide`, "no application-wide access" means the user holds no role across the whole application: ask someone who manages the application's access to give them application-wide access. Only for `records --app-wide`, `--tenant` is the fallback. For `roles create`, `roles update` and `app-identity role … --app-wide`, never move the grant to `--tenant` to get past it, because an app-tenant grant gives nothing to an app-wide token or to app-wide writes (step 2). Never retry by creating records elsewhere to get past it |
| `ENTITY_NOT_FOUND` | The `--entity` id on a `records` command isn't an entity of this application. Take the id of the entity the user meant from `multipaas model show --json` and run the command again with only that id. If `model show` no longer lists that entity, tell the user it was retired, and never write to a different entity |
| `UNAUTHORIZED` | The user lacks the permission in the web app, for example `record.create`, or the app-tenant isn't one they can reach. A command acting at `testAppTenantId` (such as `records`) gets it too when that app-tenant's environment has been removed and the developer has access at the client or application, because it never consults `environmentId`: check the environment with `multipaas envs list --app APP_ID --json`, and if it is gone, follow the `NOT_FOUND` row's `init` correction. A developer whose access is at that app-tenant gets `NOT_FOUND` instead. `roles create` and `roles update` need permission to manage the application's access across the application (`access.manage.application`). The CLI checks that permission in the default environment: a developer who manages access only in another environment is refused although they hold it there. The `access.manage.application` that `--app-wide` needs is checked in the environment the command acts in (`--env`, else `environmentId` in `multipaas.json`, else the default). All three `app-identity role` commands need `application.manage_oauth`, because they look the identity up, and the CLI checks it in the environment of the app-tenant the command acts at, or, with `--app-wide`, in the environment the command acts in (the order above). For `role list` and `role remove`, a missing `access.manage` shows up as an empty list or `NOT_FOUND`, not `UNAUTHORIZED`. `role add` and `role remove` also need `access.manage` at the app-tenant they act in, or `access.manage.application` with `--app-wide` (in the environment the command acts in). `roles create`, `roles update`, `app-identity role add` and `role remove` are also refused when the role carries a permission (for `roles update`, before or after the change) the signed-in developer doesn't hold themselves. For `roles create`, and for `roles update` adding a permission the developer lacks, leave that permission out. For `roles update` refused because the role already carries a permission the developer lacks, no change to that role is allowed, `--remove-permission` and `--name` included: ask someone who holds every permission the role carries to run it, and never retry. For `app-identity role add` and `role remove`, ask someone who holds every permission the role carries to run the command. Give the app identity a different role only if the user names it, and never pick one yourself. Never widen the developer's own access to get past it without asking the user |
| `AMBIGUOUS_ROLE` | `--role` names a key that an application role and an app-tenant role both have. The refusal names both ids with their scopes. Take the id of the role the user meant from it, or from `multipaas roles list --tenant APP_TENANT_ID --json`, where `appTenant` is `null` for the application role, and run the command again with `--role` set to that id |
| `VALIDATION` | A record's data breaks the model. The message names the fields |
| `CONFLICT` | `records update --expected-version` named a version the record has moved past: someone changed it since it was read. Run `records get` again, work out `--data` and any `--clear` again from the record it returns (add to the new count, not the old one), check the change still makes sense, and retry with its `version`. If `records get` now refuses with `NOT_FOUND`, the record was retired or the user can no longer reach it: stop and tell the user, never recreate it or write the change somewhere else. Never drop `--expected-version` to get past it |
| `CLI_ERROR` | A bad flag, for example `--data` that isn't JSON, or `--app` missing outside a directory with `multipaas.json`. Fix it and run the command again |
