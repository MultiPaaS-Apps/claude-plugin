# Import data

The `multipaas` skill covers installing the CLI, signing in and the exit codes. Follow it for those. This skill is for the import commands.

These commands need CLI 0.7.0 or later. If `multipaas --version` reports an older version, ask the user to run `brew update`, then, as a separate command, `brew upgrade multipaas`.

`import delete` and `import status --include-deleted` need CLI 0.9.0 or later. Upgrade the same way.

`--env` on the import commands needs CLI 0.13.0 or later. Upgrade the same way.

Every import command takes `--env ENV_ID`, an `id` from `multipaas envs list --app APP_ID --json`. An import belongs to one environment and writes its app-tenants and records there; without `--env` it uses `environmentId` in `multipaas.json` when that file is for the same application (CLI 1.2.0 or later), else the application's default environment. Import test data into a non-default environment first (`multipaas envs create --app APP_ID --name test --json` makes one), and give every command for that import the same `--env`. Always pass `--env ENV_ID` explicitly, `import create` included: when the user named none, use the environment the command would have picked: `environmentId` in `multipaas.json` when that file is for the same application as `--app` (CLI 1.2.0 or later), else the environment with `isDefault` in `envs list`. The import records no link to how that was resolved, so a later change to `multipaas.json` would otherwise move every follow-up and any replacement to another environment.

An import needs permission to manage the application's access (`access.manage.application`). It writes everything or nothing.

## 1. Know the target

1. Find the application: `multipaas apps list --json`. Ask the user which one if more than one fits. If none fits, offer to create one, and on a yes run `multipaas apps create --name NAME --json` and use its `application.id`. It needs CLI 0.8.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as above before running it. If it exits 1 with `UNAUTHORIZED`, the user can't create applications in that client: tell them to ask a Client manager in their organization to create it or give them permission. For `CLIENT_REQUIRED`, see the `multipaas` skill. If there is still no application, stop here: the later steps need an `APP_ID`.
2. Read its model: `multipaas model show --app APP_ID --json`. Every record you import must fit an entity there. If the model is missing an entity or field the old data needs, change the model first with the `multipaas-model` skill.

## 2. Write the files

Write one JSON-lines file per kind into one directory, one JSON object per line, from the user's old database. Ask the user how to reach that data, and write the export with their tools. Never invent rows.

| File | Each line |
|---|---|
| `tenants.jsonl` | `{"id": "OLD_ID", "name": "NAME"}`, one per app-tenant (an account, team or organisation in the old app) |
| `users.jsonl` | `{"id": "OLD_ID", "email": "EMAIL", "name": "NAME"}`. `name` is optional |
| `memberships.jsonl` | `{"user": "OLD_USER_ID", "tenant": "OLD_TENANT_ID", "role": "ROLE NAME"}`. The role must be one the application declares, named by its **name**; only application roles count, those with `appTenant` null in `multipaas roles list --app APP_ID --json`, and an app-tenant's own role never matches. `multipaas roles list --app APP_ID --json` lists them (CLI 0.11.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill), and `multipaas roles create --app APP_ID --key KEY --name "ROLE NAME" --permission PERMISSION --json` declares a missing one, with `--name` the exact name the memberships rows use; `multipaas roles update --app APP_ID --role KEY --add-permission PERMISSION --json` (needs CLI 1.1.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill) changes the permissions of one that exists; see the `multipaas-build` skill for the permission forms |
| `<entity>.jsonl` | `{"id": "OLD_ID", "tenant": "OLD_TENANT_ID", "createdBy": "OLD_USER_ID", "createdAt": "ISO 8601", "updatedAt": "ISO 8601", "deletedAt": null, "fields": {"GRAPHQL_FIELD_NAME": VALUE}}`. Name the file after the entity's name, type name or plural name from `model show`. For an app-wide record, one every app-tenant shares, write `"tenant": null` |
| `files/` | A folder beside the `.jsonl` files holding the files that records carry. Each file under `files/` becomes a file part named by its path under `files/`, with `/` separators (`files/pies/apple.jpg` is `pies/apple.jpg`). A row's file field holds that name: `"fields": {"photo": "pies/apple.jpg"}`. Needs CLI 1.4.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill |

- Ids are the old database's ids. A reference field's value is the old id of the row it points at; MultiPaaS assigns new ids to tenants and records and remaps references. A user whose email already has an account is linked to that account, which keeps its id and name. Rows can be in any order.
- An `id` is at most 1,024 bytes in UTF-8, with no control characters or unpaired surrogates.
- `fields` uses each field's `graphqlFieldName` from `model show`. An enum value is the value, not its API name. `createdBy`, the timestamps and `deletedAt` are optional; a non-null `deletedAt` imports the record as deleted.
- A record with `"tenant": null` is app-wide: it belongs to no app-tenant, and every app-tenant in its environment shares it. Leaving `tenant` out is `unknown-tenant`, not app-wide. One file can hold app-wide and tenant records together. An app-wide record can reference only app-wide records, from this import or an earlier one; a tenant record can reference its own tenant's records and app-wide ones. An app-wide record's unique key must not repeat another live app-wide line's in this import, or any live app-wide record's of that entity in the environment, however it was created. A line with a non-null `deletedAt` is left out both ways: its key is not checked, and other lines may repeat it.
- Importing app-wide records needs `record.app_wide.create` on the entity. When any of them has a non-null `deletedAt`, it also needs `record.app_wide.manage` on the entity, or `record.app_wide.edit` when the entity isn't managed (`managed` in `model show`). Checking app-wide lines that have a unique key needs permission to view that entity's app-wide records. A line that refers to an earlier import's app-wide record needs permission to view the referenced entity's app-wide records (`record.app_wide.view`, `edit` or `manage`). See the `multipaas-build` skill for the permission forms.
- An earlier import's rows can be referenced by their old ids, so tenants and users can be imported first and records later.

## 3. Import

| Command | Does |
|---|---|
| `multipaas import create --app APP_ID [--env ENV_ID] [--dir DIR] --json` | Creates an import and uploads every `.jsonl` in `DIR` and every file under `DIR/files/`. Prints `{"import": {...}}` with its `id`. If any file can't be mapped or used, nothing is created; see the refusal table below. Without `--dir` it makes an empty import, for `import add` to fill. |
| `multipaas import add --app APP_ID [--env ENV_ID] --import IMPORT_ID --kind tenants\|users\|memberships\|records\|files [--entity ENTITY_ID] [--name NAME] --file PATH --json` | Adds one file. `records` needs `--entity`, an entity id from `model show`. `files` takes `--name`, the name a row's file field uses (default: the file's base name), and no `--entity`; `--kind files` and `--name` need CLI 1.4.0 or later (check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill) |
| `multipaas import check --app APP_ID [--env ENV_ID] --import IMPORT_ID --json` | Checks every row, waits, and prints the import |
| `multipaas import run --app APP_ID [--env ENV_ID] --import IMPORT_ID --json` | Writes everything in one go, only after a clean check, waits, and prints the import |
| `multipaas import status --app APP_ID [--env ENV_ID] --import IMPORT_ID [--include-deleted] --json` | Prints the import. A deleted import is `NOT_FOUND` unless `--include-deleted` is given; then it has `deletedAt` set |
| `multipaas import delete --app APP_ID [--env ENV_ID] --import IMPORT_ID --json` | Marks the import deleted and prints it with `deletedAt` set. Its files, its problems and any data it imported stay. Refused with `DATA_IMPORT_STATE` while it is checking or importing |

The import is `{"id", "status", "files": [...], "problemCount", "problems": [{"file", "line", "sourceId", "field", "code", "message"}], "counts": [{"key", "count"}], ...}`. `check` and `run` exit 0 when they finish, whatever the result, so read `status`.

Every import command named anywhere below, `import add`, `import delete` and the rest, takes the same explicit `--env` as the one that made the import. In the table below, `import check`, `import run` and `import status` mean those commands from the table above with the same `--app`, `--env`, `--import` and `--json`.

**Keep `DIR` complete.** An import holds only what was uploaded to it. `import add` can add a part to a `check-failed` import, but nothing in the CLI replaces or removes an uploaded part, and an `import-failed` import takes no more parts, so a fix ends in a new import made from `DIR`. Keep in `DIR` everything the import needs:
- each `.jsonl` file, directly in `DIR`;
- each file a row names, under `DIR/files/` at the path the row names.

When you add a file to an import with `import add` and the add succeeds, put it in `DIR` too. First check whether a file in `DIR` already stands for the same part:
- for `tenants`, `users` or `memberships`, a `.jsonl` file named for that kind;
- for `records`, one that maps to the same entity;
- for `files`, one under `DIR/files/` whose path matches the name ignoring case.

Names always match ignoring case. Records files for different entities are different parts. If one does, don't copy it there; that would overwrite or duplicate the file. Compare the two instead, and handle it as the `DUPLICATE_DATA_IMPORT_FILE` row's same-file and different-file branches say. When a `files` name differs from that path only in case and the contents are the same, change the rows that use the added name to use the path in `DIR`.

Otherwise put it: a `files` part under `DIR/files/` at its `--name`, and a `.jsonl` file directly in `DIR`, named for its kind or entity. The one exception is a `.jsonl` file that `create --dir` refuses as `IMPORT_FILE_AMBIGUOUS` (see the refusal table). Keep it outside `DIR`, and note the `--kind`, and for `records` the `--entity`, it is added with.

**Make the import** this way, the first time and for every replacement:
1. If a `.jsonl` file sits directly in `DIR`, run `import create` with `--dir DIR`; it uploads `DIR/files/` too. If none does, because every `.jsonl` file is kept outside `DIR`, run `import create` without `--dir`, then add each file under `DIR/files/` with `import add --kind files --name PATH --file DIR/files/PATH`, where `PATH` is its path under `files/` with `/` separators.
2. Add each file kept outside `DIR` with `import add`, `--import` set to the new import's `id`, and the `--kind` and `--entity` you noted.
3. Run `import check`.

If `import create` fails after its message says the import was created (it ends "Import IMPORT_ID was created and holds …"), that import is missing every part not named there: don't check or run it. Make a new import, and offer to delete the incomplete one. If the new import fails the same way, stop and tell the user; uploads may be blocked on their network.

Pass `--env` on `import create`: for a replacement, the environment of the import it replaces, so the replacement lands beside it. "Make a new import" anywhere below means these steps, run after the fix. The new import has a new `id`.

For each `status` that `import check` or `import run` prints:

| `status` | Next |
|---|---|
| `checked` | Tell the user the counts, then ask before running `import run`. Running writes the data |
| `check-failed` | Nothing was written. Read each problem's `code`. A problem that names a file is a data problem, with or without a line: fix the data or the model, then make a new import. With a line, fix that row. `invalid-row` with "The entity for this file no longer exists" has no line: the entity was retired, probably on purpose, so ask the user: either leave that file out (out of `DIR`, or, for a file kept outside `DIR`, don't add it) and make a new import, or declare an entity with that name again with the `multipaas-model` skill (a new entity, which `create --dir` matches by name; declare it so the file's name without `.jsonl` is its name, its type name (`--type-name`) or its plural name (`--plural-name`), and add the fields the rows use with `field add --api-name` set to each key in `fields`; for a file kept outside `DIR`, note the new entity's `id` from `model show` as its `--entity`) and make a new import. `file-checksum-mismatch` has no line: the stored upload differs from what was registered, so make a new import. `check-error` and `check-timed-out` name no file: run `import check` again on the same import, and tell the user if it fails again. `check-unauthorized` means the user can no longer manage the application, or lacks read access to records the import refers to: tell them, and don't retry |
| `imported` | Done. Tell the user the counts, and that imported users are not emailed: they join their tenants at their next sign-in within 7 days of the run. After that they must be invited. A wrong imported invitation can be deleted from the console's Members screen, under Invitations, before the person signs in; they then do not join |
| `import-failed` | Nothing was written. Read each problem's `code`. A problem other than `import-error` that names a file is a data problem, with or without a line: fix the data or the model, then make a new import. With a line, fix that row. `invalid-row` with "The entity for this file no longer exists" has no line: the entity was retired, probably on purpose, so ask the user: either leave that file out (out of `DIR`, or, for a file kept outside `DIR`, don't add it) and make a new import, or declare an entity with that name again with the `multipaas-model` skill (a new entity, which `create --dir` matches by name; declare it so the file's name without `.jsonl` is its name, its type name (`--type-name`) or its plural name (`--plural-name`), and add the fields the rows use with `field add --api-name` set to each key in `fields`; for a file kept outside `DIR`, note the new entity's `id` from `model show` as its `--entity`) and make a new import. `file-checksum-mismatch` has no line: the stored upload differs from what was registered, so make a new import. `import-timed-out`, and an `import-error` whose message ends "Try again", with or without a file, leave nothing to fix: run `import check`, then `import run`, again on the same import, and tell the user if it fails again. Any other `import-error` means MultiPaaS could not write rows that passed the check: don't change the data and don't retry; tell the user, and report it with the `multipaas-feedback` skill, quoting the problem's message and the import's id. `import-unauthorized` means the user can no longer manage the application, lacks read access to records the import refers to, or lacks permission to create (or retire) the records it writes, or can't edit a record from an earlier import that a new record names as its parent; the message names the entity: tell them, and don't retry. `application-inactive` means the application was deactivated: tell the user, and don't retry |
| `checking`, `importing` | Still running. Run `import status` again in a minute; `check` and `run` stop waiting after 20 minutes with `IMPORT_STILL_RUNNING` |

Whenever a new import replaces another (a failed one, an incomplete one, or one that took a wrong file), tell the user the replaced one can now be deleted, and on a yes run `import delete` with the replaced import's id, not the new one. Deleting only hides it: `import status --include-deleted` still shows it with its files and problems. Don't delete an `imported` import to undo it: the data it wrote stays.

Common problem codes: `invalid-json`, `missing-id`, `missing-field`, `invalid-value`, `unknown-field` (not a GraphQL field name of that entity), `broken-reference` (no record with that old id that the line may reference; for an app-wide line, an earlier import's tenant record counts as missing), `cross-tenant-reference` (a reference to another tenant's record, or from an app-wide record to a tenant record in this import), `unknown-tenant` (no tenant with that old id, or no `tenant` key; write `null` for an app-wide record), `unknown-user`, `unknown-role` (the role isn't an application role, one with `appTenant` null in `multipaas roles list --app APP_ID --json`, by name), `duplicate-source-id`, `duplicate-unique-key`, `already-imported` (an earlier import already has that id), `id-too-long`, `id-invalid-character`, `invalid-character` (a NUL or an unpaired surrogate in a tenant name, a user's name or email, or a field value), `missing-file` (a file field's value doesn't name a file part of this import; put the file under `DIR/files/` at the path the row names, or correct the row to name a file there; if the file can't be found, ask the user; then make a new import), `file-too-large` (the named file is over the field's maximum size; shrink it, or raise the limit with `multipaas field update --app APP_ID --id FIELD_ID --max-file-bytes BYTES --json`, where FIELD_ID is the file field's id from `model show`), `row-too-large` (a record's fields come to more than about 3.75 MiB as UTF-8 JSON, less when the text holds many quotes or backslashes).

## When MultiPaaS refuses

A refused command exits 1 with `{"error": {"code", "message"}}`. Tell the user the message. Don't retry the same command, except where a row below says to, and then only once: if the same refusal comes back, stop and tell the user.

| Code | Meaning |
|---|---|
| `UNAUTHORIZED` | The user cannot manage this application's access |
| `IMPORT_FILE_UNMATCHED`, `IMPORT_FILE_AMBIGUOUS`, `IMPORT_DIR_EMPTY` | `create --dir` could not map `DIR`, and nothing was created. The message names the files. **`IMPORT_FILE_UNMATCHED`:** no entity is named for the file. Rename it so its name without `.jsonl` is one of its entity's names from `model show` (name, type name or plural name) that no other entity has, ignoring case. If every one of its names is shared with another entity, keep the file outside `DIR` instead, noting `--kind records --entity` set to that entity's `id`. If a file with the new name (ignoring case) is already in `DIR`, don't overwrite it: both hold that entity's rows, so combine them into the existing file as below and remove the other. If no entity in `model show` is the file's entity, ask the user whether it should exist; a retired entity isn't listed, and it may have been retired on purpose. On a yes, declare it with the `multipaas-model` skill, with the fields its rows use. On a no, take the file out of `DIR`. Then make the import. **`IMPORT_FILE_AMBIGUOUS`:** either a `tenants`, `users` or `memberships` file is also named for an entity, or a file is named for more than one entity. For a file of one entity's records, rename it to one of that entity's names that no other entity has, ignoring case, and that isn't `tenants`, `users` or `memberships` in any case, if there is one. If a file with the new name (ignoring case) is already in `DIR`, don't overwrite it: both hold that entity's rows, so combine the rows into the existing file, keeping one copy of a line both files hold, and remove the other. Lines with the same `id` and different content are `duplicate-source-id` at check. Otherwise, move the file out of `DIR` and keep it outside `DIR`, noting the `--kind` it is added with: `tenants`, `users` or `memberships` for that meaning, or `records` with `--entity` set to the entity, from `model show`, that the user says the file holds. Then make the import. **`IMPORT_DIR_EMPTY`:** no `.jsonl` file sits directly in `DIR`, and files in a subfolder don't count. Move them directly into `DIR`. If every `.jsonl` file is kept outside `DIR`, make the import without `--dir` (step 1). |
| `IMPORT_FILE_INVALID` | `create --dir` found a file that cannot be read, is empty or is over 512 MiB, or a file under `files/` whose name is over 255 bytes; the message names the files. Nothing was created. `import add --kind files` with a name over 255 bytes (the `--name`, or the file's base name when `--name` is left out) is refused the same way before anything is sent: pass a shorter `--name`. Fix each named file in `DIR` rather than removing it, because a row may name it. Export an unreadable or empty `.jsonl` file or file under `files/` again, or take it out of `DIR` if nothing needs it (no rows for a `.jsonl` file, no row naming it for a file under `files/`). For a file under `files/` whose path is over 255 bytes, move it to a shorter path under `DIR/files/` and change the rows that name it. For a file over 512 MiB, or one that can't be fixed, ask the user. Then make the import |
| `UPLOAD_REFUSED` | The upload failed. From a single `import add`: if the message says the file was removed from the import, run the same `import add` again; if it says the file is still listed, it can't be added again, so make a new import. From `import create`, the import it made is incomplete: make a new import, as above. If the new import fails the same way, stop and tell the user; uploads may be blocked on their network. |
| `DUPLICATE_DATA_IMPORT_FILE` | From `create --dir`: two files in `DIR` map to the same kind or entity, and nothing was created. The message names the files. Compare the named files' contents. If they are the same, remove all but one. If they differ, combine their rows into one file named for that kind or entity, or ask the user which rows belong. Then make the import again. From `import add`: the import already has a part of that kind (and entity), or a `files` part with that name. To tell whether it is the same file, compare the two files' contents, for example with `shasum -a 256` on both. `import status` shows only a part's name and size, which can match for different files. **Same file:** nothing more is needed. **Different file:** for a `tenants`, `users`, `memberships` or `records` part, both files may hold rows the user wants: combine their rows into one file in the place the existing part's file is kept (in `DIR`, or outside it for a file kept outside `DIR`), or ask the user which rows belong, then make a new import. For a `files` part, ask the user which file the import should have: to replace the other file, put the chosen one in its place under `DIR/files/`; for a file meant to sit beside the other, put it under a different path in `DIR/files/` and change the rows that mean it to name that path. Then make a new import. |
| `INVALID_DATA_IMPORT_FILE` | `import add` was refused before anything was sent to storage. One of three causes. **`--entity` is missing for `records`:** run it again with `--entity` set to the file's entity's `id` from `model show`. **`--entity` was given for another kind:** run it again without `--entity`. **`--entity` isn't an entity of this application:** look for the file's entity in `model show` by name. If it is listed, run it again with that entity's `id`. If it isn't listed, ask the user whether it should exist, since it may never have been declared or may have been retired on purpose. On a yes, declare it with the `multipaas-model` skill so the file's name without `.jsonl` is its name, its type name (`--type-name`) or its plural name (`--plural-name`), with the fields its rows use (`field add --api-name` set to each key in `fields`), and use the new entity's `id` from `model show` as its `--entity`, noting it for a file kept outside `DIR`. On a no, leave the file out (take it out of `DIR`, or, for a file kept outside `DIR`, don't add it). |
| `INVALID_FILE_UPLOAD` | The file is empty, over 512 MiB, or its name is too long. Fix the file as for `IMPORT_FILE_INVALID`, both its copy in `DIR` (if it has one) and the one you add. Then run the `import add` again |
| `DATA_IMPORT_STATE` | The import can't do that now (for example running before a clean check, adding a file after a run, or deleting it while it is checking or importing). Run `import status` |
| `DATA_IMPORT_EMPTY` | The import has no files |
| `FILE_UPLOAD_NOT_VERIFIED` | An upload did not complete and its file is still on the import, so it cannot be added again. Make a new import. If the new import fails the same way, stop and tell the user; uploads may be blocked on their network. |
| `PROBLEM_REPORT_UNAVAILABLE` | The full problem report could not be downloaded. Run `import status` again |
| `IMPORT_STILL_RUNNING` | Still running after 20 minutes. Run `import status` later |
| `NOT_FOUND` | No application or import with that id that the user can reach. A deleted import is `NOT_FOUND` too, unless `import status` is given `--include-deleted`. An import is found only in the environment it was made in, so an import made in the default environment isn't found from a project whose `multipaas.json` has another `environmentId` (CLI 1.2.0 or later): run the command again with the `--env` the import was created with. If no `--env` was ever given for it, or it isn't known, run `import status --app APP_ID --import IMPORT_ID --json`, with the refused command's `--include-deleted` if it had one, and with `--env` set to each environment from `multipaas envs list --app APP_ID --json` until one finds it, and use that `--env` on every later command for it, including a replacement. An environment that answers `UNAUTHORIZED` hasn't looked, because the user cannot manage the application's access there (see the `UNAUTHORIZED` row): it doesn't count as not holding the import, so don't conclude anything from it. Treat the import as missing only when every environment's `import status` ran and none found it |
