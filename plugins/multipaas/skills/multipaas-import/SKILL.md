# Import data

The `multipaas` skill covers installing the CLI, signing in and the exit codes. Follow it for those. This skill is for the import commands.

These commands need CLI 0.7.0 or later. If `multipaas --version` reports an older version, ask the user to run `brew update`, then, as a separate command, `brew upgrade multipaas`.

A value from the user or their data goes into a command in single quotes, never bare or inside double quotes, as the `multipaas` skill describes. Write each `'` in it as `'\''`, and keep a leading `~/` of a path on disk outside the quotes, but keep a `--name` wholly inside them even when it starts with `~/`. A command other than a single `multipaas` call sets it as a single-quoted variable read back as `"${X:?}"`.

`import delete` and `import status --include-deleted` need CLI 0.9.0 or later. Upgrade the same way.

`--env` on the import commands needs CLI 0.13.0 or later. Upgrade the same way.

Every import command takes `--env ENV_ID`, an `id` from `multipaas envs list --app APP_ID --json`. An import belongs to one environment and writes its app-tenants and records there; without `--env` it uses `environmentId` in `multipaas.json` when that file is for the same application (CLI 1.2.0 or later), else the application's default environment. Import test data into a non-default environment first (`multipaas envs create --app APP_ID --name test --json` makes one), and give every command for that import the same `--env`. Always pass `--env ENV_ID` explicitly, `import create` included: when the user named none, use the environment the command would have picked: `environmentId` in `multipaas.json` when that file is for the same application as `--app` (CLI 1.2.0 or later), else the environment with `isDefault` in `envs list`. The import records no link to how that was resolved, so a later change to `multipaas.json` would otherwise move every follow-up and any replacement to another environment.

An import needs permission to manage the application's access (`access.manage.application`). It writes everything or nothing.

## 1. Know the target

1. Find the application: `multipaas apps list --json`. Ask the user which one if more than one fits. If none fits, offer to create one, and on a yes run `multipaas apps create --name 'NAME' --json` and use its `application.id`. It needs CLI 0.8.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as above before running it. If it exits 1 with `UNAUTHORIZED`, the user can't create applications in that client: tell them to ask a Client manager in their organization to create it or give them permission. For `CLIENT_REQUIRED`, see the `multipaas` skill. If there is still no application, stop here: the later steps need an `APP_ID`.
2. Read its model: `multipaas model show --app APP_ID --json`. Every record you import must fit an entity there. If the model is missing an entity or field the old data needs, change the model first with the `multipaas-model` skill.

## 2. Write the files

Write one JSON-lines file per kind into one directory, one JSON object per line, from the user's old database. Ask the user how to reach that data, and write the export with their tools. Never invent rows.

| File | Each line |
|---|---|
| `tenants.jsonl` | `{"id": "OLD_ID", "name": "NAME"}`, one per app-tenant (an account, team or organisation in the old app) to create; or `{"id": "OLD_ID", "appTenant": "APP_TENANT_ID"}` to import into an app-tenant that already exists, with no `name` |
| `users.jsonl` | `{"id": "OLD_ID", "email": "EMAIL", "name": "NAME"}`. `name` is optional |
| `memberships.jsonl` | `{"user": "OLD_USER_ID", "tenant": "OLD_TENANT_ID", "role": "ROLE NAME"}`. The role must be one the application declares, named by its **name**; only application roles count, those with `appTenant` null in `multipaas roles list --app APP_ID --json`, and an app-tenant's own role never matches. `multipaas roles list --app APP_ID --json` lists them (CLI 0.11.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill), and `multipaas roles create --app APP_ID --key 'KEY' --name 'ROLE NAME' --permission PERMISSION --json` declares a missing one, with `--name` the exact name the memberships rows use; `multipaas roles update --app APP_ID --role 'KEY' --add-permission PERMISSION --json` (needs CLI 1.1.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill) changes the permissions of one that exists; see the `multipaas-build` skill for the permission forms |
| `<entity>.jsonl` | `{"id": "OLD_ID", "tenant": "OLD_TENANT_ID", "createdBy": "OLD_USER_ID", "createdAt": "ISO 8601", "updatedAt": "ISO 8601", "deletedAt": null, "fields": {"GRAPHQL_FIELD_NAME": VALUE}}`. Name the file after the entity's name, type name or plural name from `model show`. For an app-wide record, one every app-tenant shares, write `"tenant": null` |
| `files/` | A folder beside the `.jsonl` files holding the files that records carry. Each file under `files/` becomes a file part named by its path under `files/`, with `/` separators (`files/pies/apple.jpg` is `pies/apple.jpg`). A row's file field holds that name: `"fields": {"photo": "pies/apple.jpg"}`. Needs CLI 1.4.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill. Symlinks are followed with CLI 1.5.0 or later: `files/` itself, or any file or folder under it, can be a link, and each file is named by the path it is reached at under `files/`. An older CLI skips links. Before each `import create`, run `R='DIR' && find -L "${R:?}/files" -exec test -h {} \; -exec ls -ld {} \; -exec realpath {} \;`, which lists each link reached under `files/`, `DIR/files` itself and links inside a linked folder included, each followed by the real path it leads to. If it lists no link, or says there is no `files` folder, go on. If it lists any, check `multipaas --version`, and if it is older than 1.5.0, ask the user to upgrade as at the top of this skill. On 1.5.0 or later, a link to a folder uploads every file under it, whether or not a line names one: show the user each link with the real path on the line after it (a relative target after `->` is relative to the link's real folder, so it can mislead), and make the import only on their yes. For a new import from the same `DIR`, ask again only if the list differs from the one they said yes to |

- Ids are the old database's ids, and one id names one row of its entity, across every tenant and the app-wide rows. A reference field's value is the old id of the row it points at; MultiPaaS assigns new ids to tenants (or, for an `appTenant` row, uses that app-tenant) and records and remaps references. A user whose email already has an account is linked to that account, which keeps its id and name. A user row whose old id an earlier import already linked is linked again when its email is that account's, so a later import can repeat `users.jsonl`; under a different email, or once that account is deleted, it gets `already-imported`. Rows can be in any order.
- When the user already has the app-tenant the old tenant's data belongs in, map onto it rather than creating another. Find it with `multipaas tenants list --app APP_ID --env ENV_ID --json`, or create it first with `multipaas tenants create --app APP_ID --env ENV_ID --name 'NAME' --json` and take `appTenant.id`, in the environment the import runs in. Ask the user which app-tenant when more than one could fit. Point the app's config at it before the import, as for any app-tenant the app runs in (its deploy settings and app identities, and `testAppTenantId` in `multipaas.json` when that is the tenant the user tests in), so nothing has to be repointed afterwards. Then write that old tenant's row as `{"id": "OLD_ID", "appTenant": "APP_TENANT_ID"}`. Every line naming `OLD_ID` goes into that app-tenant, and so can a later import that has no tenants row for it, while that app-tenant is live and until an earlier import has put it into a second live app-tenant (then see `ambiguous-tenant` below). A row with `name` whose old id an earlier import already created or mapped onto a live app-tenant gets `already-imported`: leave its tenants row out, and its lines still resolve while that app-tenant is live (for an old id in more than one live app-tenant, see `ambiguous-tenant` below; once every app-tenant it went into is deleted, see `unknown-tenant` below). A row with `appTenant` never gets `already-imported`: onto the app-tenant an earlier import already mapped that old id to, or made from it, it selects it and records nothing new. An app-tenant takes one old id, and the check refuses a tenants row that breaks that with `duplicate-app-tenant`: follow that code's steps below, which put both old tenants' data in one app-tenant, then make a new import. If the new import's check reports `duplicate-unique-key`, records share a unique constraint's values: two lines of this import, or a line and a record already in the app-tenant (one an earlier import made, or one no import made). Ask the user which record to keep, then take one of these:
  - **Keep both.** Change one line's unique-constraint values so it no longer clashes.
  - **Keep the other record and drop this line.** First change every reference field that points at this line's entity and names its old id, in every line that resolves to this record, so it names the other record's old id. A reference resolves in its line's own app-tenant first, then app-wide, as the step 2 bullet that begins "A record's old id is unique per app-tenant" says: for a tenant record that is the lines of its app-tenant, and for an app-wide record the app-wide lines and the tenant lines whose own app-tenant has no record of that entity with that old id. Otherwise those lines get `broken-reference`. A field that points at another entity and holds the same string names a different record: leave it. This works when the other record has an old id: a line of this import, or an earlier import's record, which is named by its old id while it is live. To merge instead of dropping, copy the values you want onto the other record: into its line when it is a line of this import, or with `multipaas records update --app APP_ID --tenant APP_TENANT_ID --entity ENTITY_ID --id RECORD_ID --data 'JSON'` (`--data` is keyed by field id, from `multipaas model show`, not by the names the import lines use) when it is already in the app-tenant. Through `records update` a reference value is the referenced record's MultiPaaS id, not an old id; when that record comes from this import, set it after the import runs. That update is made outside the import, so it stays even if the import's check fails or it is not run. Tell the user this, and make the update only on their yes.
  - **Keep this line over a record already in the app-tenant.** This applies whether an earlier import made that record or no import did. The line is imported as a new record that takes the old record's place. On a managed entity, the new record must not let anyone do more than the old record lets them, except in the cases below. The import's manager is the user the line's `createdBy` names, or whoever runs the import when it names no one. The import gives them a share of their own at manage. (a) From the import until step 6, Everyone's share is wider when the entity shares new records wider than the old record's Everyone share and its sharing is still on when the import runs (steps 4 and 5). (b) From the import until step 6, the import's manager manages the new record when the old record doesn't let them manage it. That happens when no user manages it (step 3), or when they lose the group or role that let them before step 6. (c) After step 6, the import's manager keeps their share when the old record has no share at manage to Everyone or to a user or group the tab names, because a record keeps at least one share at manage. They then also manage the records step 8 moves under the new record, even if they lose the `record.manage_all` role or never managed the old record. Shares shown as "Removed" aren't carried over, which only narrows access. [Replace a record with an imported line](https://multipaas.com/docs/guides/import-existing-data/#replace-a-record-with-an-imported-line) explains why and has a worked example. Steps 1, 3, 4 and 6 apply only to an app-tenant record of a managed entity. Skip them for an app-wide record, which has no shares. Skip them too for a record of an unmanaged entity, which is reached through roles and its managed parent's shares. For that record, give the line the old record's parent. When no import made that parent, set the line's parent field to `null` and set it with `records update` after the import, as in step 8. A required parent field can't be `null` (`missing-field`), so offer keeping the other record instead. In order:
    1. Ask the user to open the old record's **Sharing** tab in the web app and tell you each share's principal and level. Read the entity's sharing of new records from `multipaas model show --app APP_ID` (`shares new records: view` or `edit`).
    2. Change the old record's unique-constraint values with `multipaas records update --app APP_ID --tenant APP_TENANT_ID --entity ENTITY_ID --id RECORD_ID --data 'JSON'` so it no longer clashes.
    3. Set the line's `createdBy` to the old id of a user who already manages the old record. Prefer a user the Sharing tab lists at manage by name. Otherwise use a member of a group it lists at manage, any member when it lists Everyone at manage, or a user whose role holds `record.manage_all` for the entity, as the default App manager role does. The tab shows a user's name, or their email when their account has no name: match it to `users.jsonl`, or ask the user for the email. If no import made that user, add them to `users.jsonl` with their account's email. Tell the user that this user also becomes the new record's creator. If no user manages the old record (its shares at manage are all to groups with no members or shown as "Removed", and no one's role, App manager included, holds `record.manage_all`), ask the user who should manage the new record, and name them or leave `createdBy` out so the importer does. Before going on, tell the user which of cases (b) and (c) above apply.
    4. When the entity shares its new records at a level the old record's Everyone share doesn't reach (none, or view against edit), offer to turn sharing off for the moment the import runs, in step 5. It needs CLI 1.7.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade. Say that this applies to the whole application: every record of the entity created while it is off, in any app-tenant or environment, is not shared with Everyone, and stays that way. Turn it off in step 5 only on the user's yes.
    5. Make the new import with this line as it is and check it, fixing and checking again until it passes. If the user said yes in step 4, run `multipaas entity update --app APP_ID --id ENTITY_ID --share-with-tenant off` right before `import run`. Whatever its exit, read the entity's `shareNewRecordsWithTenant` in `multipaas model show --app APP_ID --json`. If it is not null, sharing is on: tell the user, saying the command needs `model.edit`, which some users who can import lack. Offer to wait for someone who holds it to turn sharing off, or to run with sharing on. Then run the import. Poll `multipaas import status --app APP_ID --import IMPORT_ID --json` until `status` is neither `checking` nor `importing`: `imported` means the line was imported, and any other status means it wasn't. If it is still `checking` or `importing` more than 20 minutes after its `startedAt`, run `multipaas import check --app APP_ID --import IMPORT_ID --json`, which stops a stuck import and checks it again, and keep polling. Then, whatever the result, turn sharing back on at the level from step 1 (`--share-with-tenant view` or `edit`) if `shareNewRecordsWithTenant` was null before the run. That holds whoever turned it off, and it needs `model.edit`. Confirm it with `shareNewRecordsWithTenant` again. If turning it back on exits non-zero, or the check still shows null, tell the user at once that sharing is off for the whole application and every record of the entity created until it is back on stays unshared. Ask them to have someone who holds `model.edit` turn it back on before going on. Whenever sharing is still on when the import runs, tell the user that case (a) above applies. Go on to step 6 only when `status` is `imported`. Otherwise tell the user the line wasn't imported, fix the reported problem with them, and make a new import, starting again at step 4, where turning sharing off needs their yes again.
    6. Right after the import runs, have the new record's manager do the following on its Sharing tab, in this order:
       1. Make its Everyone share match the old record's: remove it, or share with Everyone again at the old level.
       2. Share it with each of the old record's other principals at the same levels. Skip any shown as "Removed user" or "Removed group", which can't be shared with again.
       3. Last, make the import's manager's share match theirs on the old record: share with them again at the level the tab lists for them by name, or remove their share when it doesn't list them. Skip this when it lists them at manage. This is refused until sub-step 1 or 2 has given the new record another share at manage.

       To keep both records, stop here.
    7. Wait until, when more imports were planned after this one, the last of them has run: their lines that name the old record still resolve to it until then. When a later import replaces this new record in turn, finish steps 7 to 9 for this record before starting them for that one.
    8. Find the new record's MultiPaaS id with `multipaas records list --app APP_ID --tenant APP_TENANT_ID --entity ENTITY_ID`, and change each record that references the old one, including records these imports made, to name that id with `multipaas records update --app APP_ID --tenant APP_TENANT_ID --entity ENTITY_ID --id RECORD_ID --data 'JSON'`.
    9. Delete the old record with `multipaas records delete --app APP_ID --tenant APP_TENANT_ID --entity ENTITY_ID --id RECORD_ID`. `records delete` needs CLI 1.9.0 or later: check `multipaas --version` first, and on an older CLI use `records retire`.

    Any import you make after that names the new record by this line's old id, not the old record's. The `multipaas-build` skill has these commands' flags, and the `multipaas-model` skill has `entity update`'s.

    These record and entity changes are made outside the import, so they stay even if the import's check fails or it is not run: fix the reported problem and make a new import again. Tell the user this before the first change, and make each change only on their yes. Deleting is destructive: say so when you ask.
  - **Drop this line when the other record was made by no import.** That record has no old id, so no line can name it. Instead, clear the reference fields that point at this line in the other lines. Set each to `null`, never `""` (`broken-reference`). You can also leave a field out of `fields` when it has no default; a field with a default that is left out gets the default record. After the import, set those references through the API. A required reference can't be cleared (`missing-field`): for one, keep both records or keep this line. A parent field of an unmanaged entity can be cleared, but then the record and the records under it can be read only by roles that read every record of their entity or of one above it. To merge into that record instead, copy the values you want onto it with `multipaas records update --app APP_ID --tenant APP_TENANT_ID --entity ENTITY_ID --id RECORD_ID --data 'JSON'`, then clear the references as here. Through `records update` a reference value is the referenced record's MultiPaaS id, not an old id; when that record comes from this import, set it after the import runs. That update is made outside the import, so it stays even if the import's check fails or it is not run: tell the user this, and make it only on their yes. Show the user the affected records and clear a parent field only on their yes.

  Then, except in the keep-this-line option, which makes its import in its step 5, make a new import with the edited files (`import create`).
- An `id` is at most 1,024 bytes in UTF-8, with no control characters or unpaired surrogates.
- `fields` uses each field's `graphqlFieldName` from `model show`. An enum value is the value, not its API name. `createdBy`, the timestamps and `deletedAt` are optional; a non-null `deletedAt` imports the record as deleted.
- A list field's value is a JSON array of at most 1,000 strings, such as `"tags": ["a", "b"]`; on an enum list each string is one of the enum's values. A null element, a nested array, a non-string element, more than 1,000 elements or an enum value the enum lacks is an `invalid-value` problem, so fix the line in the file and check again. A one-dimensional `text[]`, `varchar[]` or enum array column exports as a JSON array of strings; an `integer[]` exports numbers and is refused.
- A record with `"tenant": null` is app-wide: it belongs to no app-tenant, and every app-tenant in its environment shares it. Leaving `tenant` out is `unknown-tenant`, not app-wide. One file can hold app-wide and tenant records together. An app-wide record can reference only app-wide records, from this import or an earlier one; a tenant record can reference its own tenant's records and app-wide ones. An app-wide record can be the parent of a tenant record only when that record's entity is managed. An app-wide record's values must not repeat another live app-wide line's in this import, or any live app-wide record's of that entity in the environment, however it was created, for any one unique constraint of its entity. A line with a non-null `deletedAt` is left out both ways: its values are not checked, and other lines may repeat them.
- Importing app-wide records needs `record.app_wide.create` on the entity. When any of them has a non-null `deletedAt`, it also needs `record.app_wide.manage` on the entity, or `record.app_wide.edit` when the entity isn't managed (`managed` in `model show`). Checking an app-wide line that has a value in every field of one of its entity's unique constraints, and no `deletedAt`, needs permission to view that entity's app-wide records. A line that refers to an earlier import's app-wide record needs permission to view the referenced entity's app-wide records (`record.app_wide.view`, `edit` or `manage`). See the `multipaas-build` skill for the permission forms.
- An earlier import's rows can be referenced by their old ids, so tenants and users can be imported first and records later.
- A record's old id is unique per app-tenant, an app-wide record's old id is unique app-wide, and a user is held per environment (see the step 2 bullet that begins "Ids are the old database's ids"). When the user wants one old tenant's data in a second app-tenant, use the app-tenant the user already has for it (see the step 2 bullet that begins "When the user already has the app-tenant"; ask which when more than one could fit), or create one with `multipaas tenants create --app APP_ID --env ENV_ID --name 'NAME' --json` and take `appTenant.id`, and make an import with: one `tenants.jsonl` row for that old tenant, `{"id": "OLD_TENANT_ID", "appTenant": "APP_TENANT_ID"}`, and no row for any other old tenant; the record and membership lines of that tenant only, including the app-wide records those lines name, directly or through other app-wide lines, that no earlier import holds (otherwise `broken-reference`), but without the record lines an earlier import already put into that app-tenant and the app-wide records any earlier import already imported (they get `already-imported`; lines naming a record left out still resolve while it is live, and a deleted one is `broken-reference`, see that problem below), and without each membership line an earlier import into that app-tenant already held (its files list them), unless the user asks to grant it again (a repeat can re-add the person, and one for a lapsed earlier invitation does nothing, so renew that one as the `check-failed` row says); and the users it needs, as in the step 2 bullet that begins "Ids are the old database's ids": leave out a user that gets `already-imported`; the lines that name one whose email changed still resolve to the account it was linked to, and for one whose account was deleted, leaving it out makes every membership line and `createdBy` that names it `unknown-user`, so drop that user's membership lines and drop the `createdBy` (leave it out or write `null`), so whoever runs the import creates the record. A record line gets `already-imported` only when an earlier import put that old id into the same app-tenant (or app-wide, for an app-wide line), and a reference finds a record of its line's own app-tenant first, then an app-wide one, never another app-tenant's. Once that old tenant id is in a second live app-tenant, an import whose lines name it needs an `appTenant` row for it (see `ambiguous-tenant` below).
- On a managed entity, each imported record that belongs to an app-tenant is managed by the user its row names, or by whoever runs the import when the row names no one, so other members don't see it unless a role gives them `record.view_all` or the record is shared with them: its manager can share it from the record's **Sharing** tab in the web app, the app can share many with `shareRecords` (see the `multipaas-build` skill, which covers the app-identity token and the `record.manage_all` role this needs; the imported records have new ids, so list the entity's records with that token and `scope: TENANT`, which leaves out the app-wide records `shareRecords` refuses, and pass those ids, never a deleted record's. Read every page of the list first (the `multipaas-build` skill explains paging), then share the ids from all pages in batches of 100. The list holds every live record of the entity in the app-tenant, not only the imported ones, so ask the user before sharing, saying that it shares those too, and that a call sets the principal's share to the given level and lowers a higher one such as `EDIT` to `VIEW`; the API can't list existing shares, so narrow the list with `where` to the records the user means to share), or the entity can share its new records with the app-tenant. App-wide records aren't shared this way; roles read them with `record.app_wide.view`. To share the app-tenant records, have the entity share its new records before running the import. The setting shares every record created in the entity from then on, in every app-tenant and not only the imported ones, so ask the user before turning it on; `--share-with-tenant off` stops it. It needs CLI 1.7.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade. Then check the entity's `shareNewRecordsWithTenant` in `multipaas model show --app APP_ID --json`: if it is already `edit`, leave it; otherwise run `multipaas entity update --app APP_ID --id ENTITY_ID --share-with-tenant view --json`.

## 3. Import

| Command | Does |
|---|---|
| `multipaas import create --app APP_ID [--env ENV_ID] [--dir 'DIR'] --json` | Creates an import and uploads every `.jsonl` in `DIR` and every file under `DIR/files/`. Prints `{"import": {...}}` with its `id`. If any file can't be mapped or used, nothing is created; see the refusal table below. Without `--dir` it makes an empty import, for `import add` to fill. |
| `multipaas import add --app APP_ID [--env ENV_ID] --import IMPORT_ID --kind tenants\|users\|memberships\|records\|files [--entity ENTITY_ID] [--name 'NAME'] --file 'PATH' --json` | Adds one file. `records` needs `--entity`, an entity id from `model show`. `files` takes `--name`, the name a row's file field uses (default: the file's base name), and no `--entity`; `--kind files` and `--name` need CLI 1.4.0 or later (check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill) |
| `multipaas import check --app APP_ID [--env ENV_ID] --import IMPORT_ID --json` | Checks every row, waits, and prints the import |
| `multipaas import run --app APP_ID [--env ENV_ID] --import IMPORT_ID --json` | Writes everything in one go, only after a clean check, waits, and prints the import |
| `multipaas import status --app APP_ID [--env ENV_ID] --import IMPORT_ID [--include-deleted] --json` | Prints the import, with `invitations`: its `pending`, `accepted` and `lapsed` counts (CLI 1.5.0 or later; check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill). A deleted import is `NOT_FOUND` unless `--include-deleted` is given; then it has `deletedAt` set |
| `multipaas import invitations --app APP_ID [--env ENV_ID] --import IMPORT_ID --json`, or `--tenant APP_TENANT_ID` in place of `--import` | Lists the memberships that lapsed unclaimed, as `{"invitations": [...]}`. ## When MultiPaaS refuses

A refused command exits 1 with `{"error": {"code", "message"}}`. Tell the user the message. Don't retry the same command, except where a row below says to, and then only once: if the same refusal comes back, stop and tell the user.

**Values in commands.** In a command in this skill that uses `${…:?}`, never type a path or name between double quotes: a `$(…)`, a backtick or a `$` in it runs or expands, and a file name in the user's export can hold one. Set each value as a variable at the start of the same command, in single quotes, writing each `'` inside it as `'\''` (`P='files/it'\''s.png'` for `files/it's.png`), and use the variable as the command shows. For a path the user gives, write a leading `~/` outside the quotes, with the rest of the value inside them: `G=~/'exports/a.png'`, or `F=~` for `~` alone. Run the line as one command: split, it loses the variables and stops with `not set` before it changes any file or link.

**Inside DIR.** A path is inside DIR when its nearest existing folder, resolved with `F='FOLDER' && (CDPATH= cd -P -- "${F:?}" && pwd -P)`, is the same as `R='DIR' && (CDPATH= cd -P -- "${R:?}" && pwd -P)` or begins with that path followed by `/`. Before changing or writing anything at a path, apply this test to the folder that holds it. If it is outside DIR, tell the user that real folder and act only on their yes. Never move, rename or change the user's own copy of a file; copy it with `cp`.

**A path under files/.** A NAME is under `files/` only when it does not start with `/` and none of its `/`-separated parts is empty, `.` or `..`.
