# Import data

The `multipaas` skill covers installing the CLI, signing in and the exit codes. Follow it for those. This skill is for the import commands.

These commands need CLI 0.7.0 or later. If `multipaas --version` reports an older version, ask the user to run `brew update`, then, as a separate command, `brew upgrade multipaas`.

`import delete` and `import status --include-deleted` need CLI 0.9.0 or later. Upgrade the same way.

`--env` on the import commands needs CLI 0.13.0 or later. Upgrade the same way.

Every import command takes `--env ENV_ID`, an `id` from `multipaas envs list --app APP_ID --json`. An import belongs to one environment and writes its app-tenants and records there; without `--env` it uses `environmentId` in `multipaas.json` when that file is for the same application (CLI 1.2.0 or later), else the application's default environment. Import test data into a non-default environment first (`multipaas envs create --app APP_ID --name test --json` makes one), and give every command for that import the same `--env`. Always pass `--env ENV_ID` explicitly, `import create` included: when the user named none, use the environment the command would have picked: `environmentId` in `multipaas.json` when that file is for the same application as `--app` (CLI 1.2.0 or later), else the environment with `isDefault` in `envs list`. The import records no link to how that was resolved, so a later change to `multipaas.json` would otherwise move every follow-up and any replacement to another environment.

An import needs permission to manage the application's access (`access.manage.application`). It writes everything or nothing.

## 1. Know the target

1. Find the application: `multipaas apps list --json`. Ask the user which one if more than one fits. If none fits, offer to create one, and on a yes run `multipaas apps create --name NAME --json` and use its `application.id`. It needs CLI 0.8.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as above before running it. If it exits 1 with `UNAUTHORIZED`, the user can't create applications in that client: tell them to ask a Client manager in their organization to create it or give them permission. For `CLIENT_REQUIRED`, see the `multipaas` skill. If there is still no application, stop here: the later steps need an `APP_ID`.
2. Read its model: `multipaas model show --app APP_ID --json`. Every record you import must fit an entity there. If the model is missing an entity or field the old data needs, change the model first with the `multipaas-model` skill.

## 2. Write the files

Write one JSON-lines file per kind into one directory, one JSON object per line, from the user's old database. Ask the user how to reach that data, and write the export with their tools. Never invent rows.

| File | Each line |
|---|---|
| `tenants.jsonl` | `{"id": "OLD_ID", "name": "NAME"}`, one per app-tenant (an account, team or organisation in the old app) |
| `users.jsonl` | `{"id": "OLD_ID", "email": "EMAIL", "name": "NAME"}`. `name` is optional |
| `memberships.jsonl` | `{"user": "OLD_USER_ID", "tenant": "OLD_TENANT_ID", "role": "ROLE NAME"}`. The role must be one the application declares, named by its **name**; only application roles count, those with `appTenant` null in `multipaas roles list --app APP_ID --json`, and an app-tenant's own role never matches. `multipaas roles list --app APP_ID --json` lists them (CLI 0.11.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill), and `multipaas roles create --app APP_ID --key KEY --name "ROLE NAME" --permission PERMISSION --json` declares a missing one, with `--name` the exact name the memberships rows use; `multipaas roles update --app APP_ID --role KEY --add-permission PERMISSION --json` (needs CLI 1.1.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill) changes the permissions of one that exists; see the `multipaas-build` skill for the permission forms |
| `<entity>.jsonl` | `{"id": "OLD_ID", "tenant": "OLD_TENANT_ID", "createdBy": "OLD_USER_ID", "createdAt": "ISO 8601", "updatedAt": "ISO 8601", "deletedAt": null, "fields": {"GRAPHQL_FIELD_NAME": VALUE}}`. Name the file after the entity's name, type name or plural name from `model show`. For an app-wide record, one every app-tenant shares, write `"tenant": null` |
| `files/` | A folder beside the `.jsonl` files holding the files that records carry. Each file under `files/` becomes a file part named by its path under `files/`, with `/` separators (`files/pies/apple.jpg` is `pies/apple.jpg`). A row's file field holds that name: `"fields": {"photo": "pies/apple.jpg"}`. Needs CLI 1.4.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill. Symlinks are followed with CLI 1.5.0 or later: `files/` itself, or any file or folder under it, can be a link, and each file is named by the path it is reached at under `files/`. An older CLI skips links. Before each `import create`, run `R='DIR' && find -L "${R:?}/files" -exec test -h {} \; -exec ls -ld {} \; -exec realpath {} \;`, which lists each link reached under `files/`, `DIR/files` itself and links inside a linked folder included, each followed by the real path it leads to. If it lists no link, or says there is no `files` folder, go on. If it lists any, check `multipaas --version`, and if it is older than 1.5.0, ask the user to upgrade as at the top of this skill. On 1.5.0 or later, a link to a folder uploads every file under it, whether or not a line names one: show the user each link with the real path on the line after it (a relative target after `->` is relative to the link's real folder, so it can mislead), and make the import only on their yes. For a new import from the same `DIR`, ask again only if the list differs from the one they said yes to |

- Ids are the old database's ids. A reference field's value is the old id of the row it points at; MultiPaaS assigns new ids to tenants and records and remaps references. A user whose email already has an account is linked to that account, which keeps its id and name. Rows can be in any order.
- An `id` is at most 1,024 bytes in UTF-8, with no control characters or unpaired surrogates.
- `fields` uses each field's `graphqlFieldName` from `model show`. An enum value is the value, not its API name. `createdBy`, the timestamps and `deletedAt` are optional; a non-null `deletedAt` imports the record as deleted.
- A record with `"tenant": null` is app-wide: it belongs to no app-tenant, and every app-tenant in its environment shares it. Leaving `tenant` out is `unknown-tenant`, not app-wide. One file can hold app-wide and tenant records together. An app-wide record can reference only app-wide records, from this import or an earlier one; a tenant record can reference its own tenant's records and app-wide ones. An app-wide record's values must not repeat another live app-wide line's in this import, or any live app-wide record's of that entity in the environment, however it was created, for any one unique constraint of its entity. A line with a non-null `deletedAt` is left out both ways: its values are not checked, and other lines may repeat them.
- Importing app-wide records needs `record.app_wide.create` on the entity. When any of them has a non-null `deletedAt`, it also needs `record.app_wide.manage` on the entity, or `record.app_wide.edit` when the entity isn't managed (`managed` in `model show`). Checking an app-wide line that has a value in every field of one of its entity's unique constraints, and no `deletedAt`, needs permission to view that entity's app-wide records. A line that refers to an earlier import's app-wide record needs permission to view the referenced entity's app-wide records (`record.app_wide.view`, `edit` or `manage`). See the `multipaas-build` skill for the permission forms.
- An earlier import's rows can be referenced by their old ids, so tenants and users can be imported first and records later.

## 3. Import

| Command | Does |
|---|---|
| `multipaas import create --app APP_ID [--env ENV_ID] [--dir DIR] --json` | Creates an import and uploads every `.jsonl` in `DIR` and every file under `DIR/files/`. Prints `{"import": {...}}` with its `id`. If any file can't be mapped or used, nothing is created; see the refusal table below. Without `--dir` it makes an empty import, for `import add` to fill. |
| `multipaas import add --app APP_ID [--env ENV_ID] --import IMPORT_ID --kind tenants\|users\|memberships\|records\|files [--entity ENTITY_ID] [--name NAME] --file PATH --json` | Adds one file. `records` needs `--entity`, an entity id from `model show`. `files` takes `--name`, the name a row's file field uses (default: the file's base name), and no `--entity`; `--kind files` and `--name` need CLI 1.4.0 or later (check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top of this skill) |
| `multipaas import check --app APP_ID [--env ENV_ID] --import IMPORT_ID --json` | Checks every row, waits, and prints the import |
| `multipaas import run --app APP_ID [--env ENV_ID] --import IMPORT_ID --json` | Writes everything in one go, only after a clean check, waits, and prints the import |
| `multipaas import status --app APP_ID [--env ENV_ID] --import IMPORT_ID [--include-deleted] --json` | Prints the import. A deleted import is `NOT_FOUND` unless `--include-deleted` is given; then it has `deletedAt` set |
| `multipaas import delete --app APP_ID [--env ENV_ID] --import IMPORT_ID --json` | Marks the import deleted and prints it with `deletedAt` set. Its files, its problems and any data it imported stay. Refused with `DATA_IMPORT_STATE` while it is checking or importing |

The import is `{"id", "status", "files": [...], "problemCount", "problems": [{"file", "line", "sourceId", "field", "code", "message"}], "counts": [{"key", "count"}], ...}`. `check` and `run` exit 0 when they finish, whatever the result, so read `status`.

Every import command named anywhere below, `import add`, `import delete` and the rest, takes the same explicit `--env` as the one that made the import. In the table below, `import check`, `import run` and `import status` mean those commands from the table above with the same `--app`, `--env`, `--import` and `--json`.

**Keep `DIR` complete.** An import holds only what was uploaded to it. `import add` can add a part to a `check-failed` import, but nothing in the CLI replaces or removes an uploaded part, and an `import-failed` import takes no more parts, so a fix ends in a new import made from `DIR`. Keep in `DIR` everything the import needs:
- each `.jsonl` file, directly in `DIR`;
- each file a row names, under `DIR/files/` at the path the row names.

When you add a file to an import with `import add` and the add succeeds, put it in `DIR` too. First check whether a file in `DIR` already stands for the same part:
- for `tenants`, `users` or `memberships`, a `.jsonl` file named for that kind;
- for `records`, one that maps to the same entity;
- for `files`, one under `DIR/files/` whose path matches the name ignoring case.

Names always match ignoring case. Records files for different entities are different parts. If one does, don't copy it there; that would overwrite or duplicate the file. Compare the two instead, and handle it as the `DUPLICATE_DATA_IMPORT_FILE` row's same-file and different-file branches say. When a `files` name differs from that path only in case and the contents are the same, change the rows that use the added name to use the path in `DIR`.

Otherwise put it: a `files` part under `DIR/files/` at its `--name`, and a `.jsonl` file directly in `DIR`, named for its kind or entity. The one exception is a `.jsonl` file that `create --dir` refuses as `IMPORT_FILE_AMBIGUOUS` (see the refusal table). Keep it outside `DIR`, and note the `--kind`, and for `records` the `--entity`, it is added with.

**Make the import** this way, the first time and for every replacement:
1. If a `.jsonl` file sits directly in `DIR`, run `import create` with `--dir DIR`; it uploads `DIR/files/` too. If none does, because every `.jsonl` file is kept outside `DIR`, run `import create` without `--dir`, then add each file under `DIR/files/` with `import add --kind files --name PATH --file DIR/files/PATH`, where `PATH` is its path under `files/` with `/` separators.
2. Add each file kept outside `DIR` with `import add`, `--import` set to the new import's `id`, and the `--kind` and `--entity` you noted.
3. Run `import check`.

If `import create` fails after its message says the import was created (it ends "Import IMPORT_ID was created and holds …"), that import is missing every part not named there: don't check or run it. Make a new import, and offer to delete the incomplete one. If the new import fails the same way, stop and tell the user; uploads may be blocked on their network.

Pass `--env` on `import create`: for a replacement, the environment of the import it replaces, so the replacement lands beside it. "Make a new import" anywhere below means these steps, run after the fix. The new import has a new `id`.

For each `status` that `import check` or `import run` prints:

| `status` | Next |
|---|---|
| `checked` | Tell the user the counts, then ask before running `import run`. Running writes the data |
| `check-failed` | Nothing was written. Read each problem's `code`. A problem that names a file is a data problem, with or without a line: fix the data or the model, then make a new import. With a line, fix that row. `invalid-row` with "The entity for this file no longer exists" has no line: the entity was retired, probably on purpose, so ask the user: either leave that file out (out of `DIR`, or, for a file kept outside `DIR`, don't add it) and make a new import, or declare an entity with that name again with the `multipaas-model` skill (a new entity, which `create --dir` matches by name; declare it so the file's name without `.jsonl` is its name, its type name (`--type-name`) or its plural name (`--plural-name`), and add the fields the rows use with `field add --api-name` set to each key in `fields`; for a file kept outside `DIR`, note the new entity's `id` from `model show` as its `--entity`) and make a new import. `file-checksum-mismatch` has no line: the stored upload differs from what was registered, so make a new import. `check-error` and `check-timed-out` name no file: run `import check` again on the same import, and tell the user if it fails again. `too-many-files` names no file either: the import names more than 11,000 files or 99 GiB, counting a file once for each line and field that names it. Before splitting, tell the user the data will land as several imports, each all-or-nothing on its own: one that already ran stays written if a later one fails. Then plan every import before you make or run the first, and split the lines. A row names another through `tenant`, `createdBy`, a membership's user and tenant, a reference or a parent field. Rows that can each reach the other by following names, directly or through other rows, must all share one import. Count a name that points at a record with a non-null `deletedAt` as pointing both ways, because a later import can't name a deleted record. For example, A names B, B names C and C names A share one import. So do a deleted record D, every row that names D, and every row on a path of names between those rows. If such a group still exceeds a limit, stop before making or running any import: tell the user the data can't be split to fit, and offer to report it with the `multipaas-feedback` skill. Put each tenant, user, record and membership in one import only. Put a row in the same import as every row that names it, or in an earlier one, through `tenant`, `createdBy`, a membership's user and tenant, a reference or a parent field. A later import that lists a row an earlier import already holds gets `already-imported`: remove that line, and the lines that name it still resolve while it is live. A membership listed again in a later import is not reported, and the check reports `duplicate-membership` only for a repeat within one import. The repeat is skipped only while the earlier invitation for that tenant, user and role is neither accepted nor deleted. Otherwise it creates a new invitation, which re-adds or re-invites the person at their next sign-in. To leave out a line, remove it, and every line that names it, directly or through other lines, from this import and from every later import you planned. If any import of a split fails, the first included, because a row it names is in a file of an import you planned but haven't run (`unknown-user` or `unknown-tenant` for a user or tenant, `broken-reference` for a record), the plan was wrong. Plan again every import you haven't run, this one included, under the rules above, and make a new import from the first of them. `unknown-user` or `unknown-tenant` means no live user or tenant with that id is in this import or in an import that already ran. If an import that already ran holds it, it has been deactivated since, and listing it again gets `already-imported`: ask the user, then drop a record's `createdBy`, so that whoever runs the import creates the record, leave out a membership, or, for a tenant, leave out every line that names it. If it is in none of the files, ask the user whether to supply the row in this import's replacement, drop the `createdBy`, or leave out the line. In a later import, `broken-reference` for a record an import that already ran holds depends on that record's line in the import's file. A line can name a record of its own tenant or an app-wide record, and an app-wide line can name only app-wide records. If the record is one the line can name, it has been deleted, whether its line has a non-null `deletedAt` or it was deleted since. A later import can't name a deleted record: tell the user, then leave out the line. Don't list the record again: it gets `already-imported`. If the record is one the line can't name (it is in another tenant, or it is a tenant's record and the line is app-wide or in a tenant created in this import), the reference is wrong: fix it. Keep a line with its parent, its reference targets and, for an entity with a unique constraint, its tenant wherever you can. A later import needs more access than one import would. A line whose parent is in an earlier import needs edit access to that parent when it runs, and `import-unauthorized` comes after the check has passed. Give each import only the files its lines name, under its own `DIR/files/`, and make an import from each. Check and run each import before making the next, because a later import resolves an earlier one's rows only after it has run. A split that fails is handled by its status and code as the rows of this table say, and the later splits wait until it has imported. `check-unauthorized` means the user can no longer manage the application, or lacks read access to an entity's records that the check reads: the records a line references or has as its parent from an earlier import, and for an entity with a unique constraint the records already in the tenant or app-wide scope the line goes in. Tell them what the message names. Once someone who can grant that access has granted it, run `import check` again on the same import; until then, don't retry |
| `imported` | Done. Tell the user the counts, and that imported users are not emailed: they join their tenants at their next sign-in within 7 days of the run. After that they must be invited. A wrong imported invitation can be deleted from the console's Members screen, under Invitations, before the person signs in; they then do not join |
| `import-failed` | Nothing was written. Read each problem's `code`. A problem other than `import-error` that names a file is a data problem, with or without a line: fix the data or the model, then make a new import. With a line, fix that row. `invalid-row` with "The entity for this file no longer exists" has no line: the entity was retired, probably on purpose, so ask the user: either leave that file out (out of `DIR`, or, for a file kept outside `DIR`, don't add it) and make a new import, or declare an entity with that name again with the `multipaas-model` skill (a new entity, which `create --dir` matches by name; declare it so the file's name without `.jsonl` is its name, its type name (`--type-name`) or its plural name (`--plural-name`), and add the fields the rows use with `field add --api-name` set to each key in `fields`; for a file kept outside `DIR`, note the new entity's `id` from `model show` as its `--entity`) and make a new import. `file-checksum-mismatch` has no line: the stored upload differs from what was registered, so make a new import. `import-timed-out`, and an `import-error` whose message ends "Try again", with or without a file, leave nothing to fix: run `import check`, then `import run`, again on the same import, and tell the user if it fails again. Any other `import-error` means MultiPaaS could not write rows that passed the check: don't change the data and don't retry; tell the user, and report it with the `multipaas-feedback` skill, quoting the problem's message and the import's id. `import-unauthorized` means the user can no longer manage the application, lacks read access to an entity's records that the run reads again (the ones `check-unauthorized` names), or lacks permission to create (or retire) the records it writes, or can't edit a record from an earlier import that a new record names as its parent; the message names the entity: tell them. Once someone who can grant that access has granted it, run `import check`, then `import run`, again on the same import; until then, don't retry. `application-inactive` means the application was deactivated: tell the user, and don't retry, because a deactivated application accepts no import: the data has to go into an active application |
| `checking`, `importing` | Still running. Run `import status` again in a minute; `check` and `run` stop waiting after 20 minutes with `IMPORT_STILL_RUNNING` |

Whenever a new import replaces another (a failed one, an incomplete one, or one that took a wrong file), tell the user the replaced one can now be deleted, and on a yes run `import delete` with the replaced import's id, not the new one. Deleting only hides it: `import status --include-deleted` still shows it with its files and problems. Don't delete an `imported` import to undo it: the data it wrote stays.

Common problem codes: `invalid-json`, `missing-id`, `missing-field`, `invalid-value`, `unknown-field` (not a GraphQL field name of that entity), `broken-reference` (no record with that old id that the line may reference; for an app-wide line, an earlier import's tenant record counts as missing), `cross-tenant-reference` (a reference to another tenant's record, or from an app-wide record to a tenant record in this import), `unknown-tenant` (no tenant with that old id, or no `tenant` key; write `null` for an app-wide record), `unknown-user`, `unknown-role` (the role isn't an application role, one with `appTenant` null in `multipaas roles list --app APP_ID --json`, by name), `duplicate-source-id`, `duplicate-unique-key`, `already-imported` (an earlier import already has that id), `id-too-long`, `id-invalid-character`, `invalid-character` (a NUL or an unpaired surrogate in a tenant name, a user's name or email, or a field value), `missing-file` (a file field's value doesn't name a file part of this import; if `DIR/files`, or any folder or file on the path the line names under it, is a symlink (`R='DIR' && find "${R:?}/files" -type l` lists it, or `DIR/files` itself is one) and `multipaas --version` is older than 1.5.0, the CLI skipped it, so ask the user to upgrade as at the top of this skill; otherwise copy it with `R='DIR' N='NAME' S='SOURCE' && mkdir -p "$(dirname -- "${R:?}/files/${N:?}")" && cp -- "${S:?}" "${R:?}/files/${N:?}"` (SOURCE is the user's copy of the file), where NAME is the name the line holds (its path under `files/`), after applying **Inside DIR** to the folder that will hold it, or correct the row to name a file there; if the file can't be found, ask the user, unless the user has already said it no longer exists (for example, after a gone link was removed); in that case go straight to the step below for a file that no longer exists. If the user says the file no longer exists, dropping a line breaks every line that names its record, so work out what dropping it means before asking. Start with that record as dropped. Find each line that names a dropped record: parse the `.jsonl` files of this import and, when it is one of a planned split, of every later import you planned, with a JSON parser such as `jq` or Python, not grep, and match a reference field's value to the record's `id` within the entity that field references (`multipaas model show`). If that field accepts null (it is neither required nor not-null), the line keeps its record with the field set to null. Otherwise the line is dropped too, and its record counts as dropped. Repeat until no line names a dropped record. Then ask the user once, showing the lines, in every one of those imports, that would be dropped and the fields that would be set to null: drop the record that way, or keep it by leaving its file out of the line (or setting it to `null`) for an optional file field, or by giving a replacement file, copied with `R='DIR' N='NAME' S='SOURCE' && mkdir -p "$(dirname -- "${R:?}/files/${N:?}")" && cp -- "${S:?}" "${R:?}/files/${N:?}"`, where NAME is the name the line holds (its path under `files/`), after applying **Inside DIR** to the folder that will hold it, for a required one. Act only on the answer, applied to each of those imports' files. Then make a new import), `file-too-large` (the named file is over the field's maximum size; shrink it, or raise the limit with `multipaas field update --app APP_ID --id FIELD_ID --max-file-bytes BYTES --json`, where FIELD_ID is the file field's id from `model show`), `row-too-large` (a record's fields come to more than about 3.75 MiB as UTF-8 JSON, less when the text holds many quotes or backslashes), `too-many-files` (more than 11,000 files or 99 GiB in one import, counting a file once per line and field naming it; split the data across several imports, as the `check-failed` row says). `duplicate-unique-key` names the fields of the one unique constraint the line breaks, against another line or an existing record; a line can get one per constraint. It is also reported when another write took the same values between the check and the run.

## When MultiPaaS refuses

A refused command exits 1 with `{"error": {"code", "message"}}`. Tell the user the message. Don't retry the same command, except where a row below says to, and then only once: if the same refusal comes back, stop and tell the user.

**Values in commands.** In a command in this skill that uses `${…:?}`, never type a path or name between double quotes: a `$(…)`, a backtick or a `$` in it runs or expands, and a file name in the user's export can hold one. Set each value as a variable at the start of the same command, in single quotes, writing each `'` inside it as `'\''` (`P='files/it'\''s.png'` for `files/it's.png`), and use the variable as the command shows. For a path the user gives, write a leading `~/` outside the quotes, with the rest of the value inside them: `G=~/'exports/a.png'`, or `F=~` for `~` alone. Run the line as one command: split, it loses the variables and stops with `not set` before it changes any file or link.

**Inside DIR.** A path is inside DIR when its nearest existing folder, resolved with `F='FOLDER' && (CDPATH= cd -- "${F:?}" && pwd -P)`, is the same as `R='DIR' && (CDPATH= cd -- "${R:?}" && pwd -P)` or begins with that path followed by `/`. Before changing or writing anything at a path, apply this test to the folder that holds it. If it is outside DIR, tell the user that real folder and act only on their yes. Never move, rename or change the user's own copy of a file; copy it with `cp`.

| Code | Meaning |
|---|---|
| `UNAUTHORIZED` | The user cannot manage this application's access |
| `IMPORT_FILE_UNMATCHED`, `IMPORT_FILE_AMBIGUOUS`, `IMPORT_DIR_EMPTY` | `create --dir` could not map `DIR`, and nothing was created. The message names the files. **`IMPORT_FILE_UNMATCHED`:** no entity is named for the file. Rename it so its name without `.jsonl` is one of its entity's names from `model show` (name, type name or plural name) that no other entity has, ignoring case. If every one of its names is shared with another entity, keep the file outside `DIR` instead, noting `--kind records --entity` set to that entity's `id`.
