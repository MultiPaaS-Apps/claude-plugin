# Change the model

The `multipaas` skill covers installing the CLI, signing in and the exit codes. Follow it for those. This skill is for the model commands.

These commands need CLI 0.5.0 or later. If `multipaas --version` reports an older version, ask the user to run `brew update`, then, as a separate command, `brew upgrade multipaas`.

A value from the user or their data goes into a command in single quotes, never bare or inside double quotes, as the `multipaas` skill describes. Write each `'` in it as `'\''`, and keep a leading `~/` of a path on disk outside the quotes.

Every change acts on the live model of one application, as the signed-in developer, with exactly their permissions in the MultiPaaS web app. A change takes effect immediately and mints a new API version. A version can also be made without a model change, to get newer API features: see the `multipaas-upgrade` skill. There is no publish step.

## Before changing anything

1. Find the application: `multipaas apps list --json`. Ask the user which one if more than one fits. If none fits, offer to create one, and on a yes run `multipaas apps create --name 'NAME' --json` and use its `application.id`. It needs CLI 0.8.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as above before running it. If it exits 1 with `UNAUTHORIZED`, the user can't create applications in that client: tell them to ask a Client manager in their organization to create it or give them permission. For `CLIENT_REQUIRED`, see the `multipaas` skill. If there is still no application, stop here: the later steps need an `APP_ID`.
2. Read its model: `multipaas model show --app APP_ID --json`. Use the ids it prints. Never guess an id.
3. Say what you are about to change, in a sentence, before running a command that deletes something.

If `multipaas model show` exits 1 with `CLI_ERROR` and an `unknown command` message, the CLI is older than 0.2.0. Ask the user to run `brew update`, then, as a separate command, `brew upgrade multipaas`.

## Commands

`entity delete`, `enum delete`, `field delete` and `constraint delete` need CLI 1.9.0 or later: check `multipaas --version` first. On an older CLI, run `entity retire`, `enum retire`, `field retire` and `constraint retire` instead, which do the same.

All take `--app APP_ID --json`. On exit 0, a change prints `{"entity" | "enumType" | "field" | "constraint": {...}, "apiVersion": "ID"}`.

| Command | Does |
|---|---|
| `multipaas model show` | `{"apiVersion": "ID", "entities": [{"id", "name", "graphqlTypeName", "graphqlPluralName", "managed", "shareNewRecordsWithTenant", "fields": [...], "constraints": [...]}], "enums": [{"id", "name", "graphqlTypeName", "values": [{"value", "graphqlName"}]}]}`. `apiVersion` is `""` before the first change |
| `multipaas entity create --name 'NAME' [--type-name 'T'] [--plural-name 'P']` | Declare an entity |
| `multipaas entity update --id ENTITY_ID [--name] [--type-name] [--plural-name] [--managed[=false]] [--share-with-tenant view\|edit\|off]` | Rename an entity, change whether it is managed, or share its new records with the app-tenant |
| `multipaas entity delete --id ENTITY_ID` | Delete an entity |
| `multipaas enum create --name 'NAME' --values 'a,b=API_NAME' [--type-name 'T']` | Declare an enum. Each value is `VALUE` or `VALUE=API_NAME`, split on the last `=`, so a value that contains `=` needs a trailing `=API_NAME`; the API name defaults to SCREAMING_SNAKE_CASE of the value |
| `multipaas enum update --id ENUM_ID [--name] [--type-name] [--values 'a,b=API_NAME']` | Change an enum. `--values` takes the same `VALUE` or `VALUE=API_NAME` form and replaces the whole list, so a value not given is removed (refused while a record or a field default holds it), and an API name not given goes back to its default |
| `multipaas enum delete --id ENUM_ID` | Delete an enum |
| `multipaas field add --entity ENTITY_ID --type TYPE [--name] [--api-name] [--required] [--default 'VALUE'] [--not-null] [--list] [--enum-type ENUM_ID] [--references ENTITY_ID] [--related FIELD_ID] [--parent] [--max-file-bytes N] [--lifecycle]` | Add a field |
| `multipaas field update --id FIELD_ID [--type] [--name] [--api-name] [--required[=false]] [--default 'VALUE' \| --clear-default] [--not-null \| --nullable] [--enum-type ENUM_ID] [--references] [--related] [--parent[=false]] [--max-file-bytes N]` | Change a field. Only the flags given change |
| `multipaas field delete --id FIELD_ID` | Delete a field |
| `multipaas constraint add --entity ENTITY_ID --fields FIELD_ID,FIELD_ID` | Make those fields unique together. An entity can have up to 10 unique constraints, each over a different set of fields |
| `multipaas constraint delete --id CONSTRAINT_ID` | Delete a constraint |

An entity's or enum's GraphQL type name comes from its name unless `--type-name` gives one. It can't be the name of a type the generated API has for itself, such as `Query`, `User`, `File`, `FileUpload` or `HttpHeader`: the change is refused with `MODEL_GENERATION_FAILED`. Give the entity or enum another `--type-name`. Versions made before file fields allowed `File`, `FileUpload` and `HttpHeader`, so an older model can already have one. Read each entity's and enum's `graphqlTypeName` from the model you read in step 2 (`multipaas model show --app APP_ID --json`) to see which have one of those names. Then every model change that leaves one of them in place is refused: rename it with `entity update --id ENTITY_ID --type-name 'NEW_NAME'` or `enum update --id ENUM_ID --type-name 'NEW_NAME'`, or delete it if the user no longer needs it and nothing uses it. Ask the user first. The app stays on its pin either way, but once it moves to a version made after the change, its code has to use the new type name after a rename, and after a delete the type and its records aren't in that version. When that read shows more than one of them, a change to one leaves another, so it's refused too: tell the user, and offer to report it with the `multipaas-feedback` skill. If the change is refused, read the refusal. When the name it's about is the type name just given, or one the generated API makes from it such as `updateAsset` or `AssetPage` for `Asset`, pick another. When a delete is refused because something still uses the entity or enum or links to it, rename it instead. If the rename was already refused, tell the user, and offer to report both refusals with the `multipaas-feedback` skill. When it names another of `File`, `FileUpload` or `HttpHeader`, one on an entity or enum you didn't change, the model has more than one: tell the user, and offer to report it with the `multipaas-feedback` skill. Don't offer a delete. When it's `UNAUTHORIZED`, `NOT_FOUND`, `ENTITY_NOT_FOUND` or `ENUM_NOT_FOUND`, handle it as the table below says. When it's anything else, the generated API has a second thing it refuses. If the user no longer needs the entity and no delete has been refused, offer to delete it, which may clear both. Otherwise tell the user, and offer to report the refusals with the `multipaas-feedback` skill.

Every entity starts managed: each record is its own unit of access, and its creator manages it. Turn managed off (`entity update --managed=false`) only for an entity that has a required parent field (a reference field with `--parent` and `--required`, from `field add` or `field update`); its records then follow the parent record's access, including records other users added. On an unmanaged entity `record.edit_all` is enough to delete records, and sharing one takes managing the nearest record up its parent chain whose entity is managed. Creating a child, or moving it to another parent, takes edit access to that parent. A child follows its parent only while the parent is a live record of the same app-tenant with access of its own (a managed record, or one that follows a parent in turn). Otherwise (no parent value, a deleted parent, an app-wide parent, or a parent with no access of its own) not even its creator can read it, and only roles that read every record of its entity or of an entity above it in the parent chain can. An app-wide record can be the parent only of a record whose entity is managed, so a tenant record of an unmanaged entity can't be written with an app-wide parent, and `entity update --managed=false` is refused while any of the entity's live tenant records has an app-wide parent.

On a managed entity, `entity update --share-with-tenant view` (or `edit`) shares each new record with everyone in its app-tenant, whoever creates it: a member, an app identity or an import. Records created earlier aren't shared; share them with `shareRecords` (see the `multipaas-build` skill), and `off` stops it. Turn it off before making the entity unmanaged. It needs CLI 1.7.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade.

`TYPE` is one of `text`, `number`, `boolean`, `timestamp`, `enum` (with `--enum-type`, an enum's id from `model show`; create the enum first with `enum create`, and one enum can be shared by several fields), `reference` (with `--references`, the target entity's id), `related` (with `--related`, the id of a reference field on another entity that points here) or `file` (a file on each record, with an optional `--max-file-bytes` for its largest size in whole bytes, up to 512 MiB, which is the default; `file`, and `--max-file-bytes` on `field add` and `field update`, need CLI 1.1.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as above). A file field can be required, but it has no default and can't be not null. The `multipaas-build` skill says how an app uploads and reads a file.

A `text` or `enum` field can hold a list of values: add `--list` when you add it. It can't be added or removed later, so ask the user before adding a field as a list. A list keeps its order and can repeat a value, and a list field can't be part of a unique constraint or be used in `orderBy`. `--list` needs CLI 1.5.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as above.

A field can have a default: the value a record gets when it is written without one. Set it with `--default 'VALUE'` on `field add` or `field update`, and remove it with `field update --clear-default`, which a not-null field refuses with VALIDATION "a not-null field needs a default value": give `--clear-default --nullable` in one `field update` to do both. Write the value as the field's type: a number for a number field, `true` or `false` for a boolean field, one of the enum's values for an enum field, an ISO timestamp such as `2026-01-01T00:00:00Z` for a timestamp field, a record id for a reference field, and the text itself for a text field. A file or related field has no default, and the CLI refuses `--default` for one. `--not-null` makes the field always hold a value. It needs a default, given with `--default` or already set, and turning it on writes the default onto every existing record that has no value. `field update --nullable` turns it off. A reference, related or file field can't be not null. A list's default is a JSON array, such as `--default '["a"]'`. `model show` lists each field's default and whether it is not null, and marks a list field `list-of-text` or `list-of-enum`. `--default`, `--clear-default`, `--not-null` and `--nullable` need CLI 1.4.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as above.

A `related` field is how a record lists the records that reference it: to list a cookbook's recipes, add a `related` field to Cookbook with `--related` set to Recipe's reference field to Cookbook. It adds no data. The generated API pages through those records on the parent.

## After a change

Tell the user what changed and the `apiVersion` it printed. That is the API version the model is at after the change. An app the user builds pins a version, so a change never breaks an app already built on an earlier one.

Changing a field's `--api-name` renames it in the API, in the new version only. An app pinned to an earlier version keeps the old name, and its records carry over, because records are keyed by field id. Changing only `--name` leaves the API as it is.

Exit 0 with `"apiVersion": ""` means the change was made but its version could not be read. Run `multipaas model show --app APP_ID --json` to get the current version.

## When MultiPaaS refuses

A change MultiPaaS refuses exits 1 with `{"error": {"code", "message"}}` and a code other than `CLI_ERROR`, and nothing changed. Tell the user the message as it is. It is the platform's own reason. Don't retry the same change. Suggest what would make it allowed, where the code says:

| Code | Meaning |
|---|---|
| `UNAUTHORIZED` | The user may not change this application's model: they lack `model.edit` on the application. It counts only from a role granted in every environment, never from a role granted in one environment. Making a field a parent, or changing what a parent field references (its `--references`, or a `--type` that is not `reference`), also needs `access.manage.application`: `field add --parent`, and any `field update` that leaves the field a parent while giving it a new parent link. Both are the same as in the web app. `access.manage.application` here counts only from a role granted in every environment, the same way. Only someone who manages the application's access can grant it |
| `NOT_FOUND` | No application with that id that the user can reach, or no entity, enum, field or constraint with the id given to `--id` |
| `ENTITY_NOT_FOUND` | `--entity` or `--references` names no entity in this application |
| `ENUM_NOT_FOUND` | `--id` of `enum update` or `enum delete` names no enum in this application |
| `MODEL_GENERATION_FAILED` | The platform could not generate the API for the changed model, so the change was not made. Tell the user the message. When a create, or a rename to a new type name, gives an entity or enum a type name the generated API has for itself, give it another `--type-name` (see above). When an existing entity or enum already has one of those type names, follow the paragraph about those names above instead. A message naming `StringListFilter` or `<Enum>ListFilter` means a list field needs that filter type, and another type's name makes the same name. Entity `StringList` makes `StringListFilter`. Entity `StatusList` makes `StatusListFilter`, which a list over enum `Status` needs. If the write gives an entity or enum a type name (a create, or a `--type-name` change), pick another type name for it. If it adds a list field, ask the user whether to give the named entity or enum another `--type-name`, which changes the app's API, or not to make the field a list. If it changes an existing list field's type or enum, ask whether to give the named entity or enum another `--type-name`, or to keep the field's current type and enum |
| `DUPLICATE_ENTITY_NAME`, `DUPLICATE_ENUM_NAME`, `DUPLICATE_FIELD_NAME` | That name already exists |
| `DUPLICATE_CONSTRAINT` | A unique constraint on that set of fields already exists. `model show` lists the entity's constraints |
| `UNSAFE_FIELD_CHANGE` | The change would rewrite existing records. Add a new field instead |
| `ENUM_VALUE_IN_USE` | `enum update --values` would remove a value that a record or a field default still holds. Deleted records and records in other app-tenants count too. The message lists every value the update would remove, not only the ones still held. Keep those values in `--values` |
| `ENTITY_IN_USE`, `ENUM_IN_USE`, `FIELD_IN_CONSTRAINT`, `REFERENCE_HAS_RELATED_FIELD` | Something else depends on it. The message names what to delete first. When the entity or enum being deleted has a type name the generated API has for itself, follow the paragraph about those names above instead |
| `EXISTING_RECORDS_VIOLATE_CONSTRAINT` | Existing records already break the uniqueness. Uniqueness holds within one app-tenant and among one environment's app-wide records, but adding a constraint checks every live environment. Follow "A uniqueness refusal" below |
| `CONSTRAINT_LIMIT` | The entity already has 10 unique constraints, the most it can have. Ask the user which of the entity's constraints to delete with `constraint delete`, or whether to drop the new one instead. Delete the one the user picks, then run `constraint add` again. Never delete one on your own |
| `VALIDATION` | An input is invalid. The message names the fields. A `list` rule means one of four things. `--list` was used on a field that isn't text or enum: add the field with `--type text` or `--type enum`. A list field's type was changed to something other than text or enum: keep it text or enum. A list field was named in a unique constraint: leave it out of the constraint. Or a list has more than 1,000 values: shorten it. Then run the command again. An `app-wide-parent` rule means some of the entity's live tenant records name an app-wide record as their parent, a deleted one included; a deleted tenant record doesn't count. It is refused on field `managed` for `entity update --managed=false`, and on field `isParent` for a `field update` that makes a reference field the parent of an unmanaged entity. The message names no records, and they can be in any environment and app-tenant of the application, including records you can't read and records whose parent is a deleted app-wide record, which no listing marks as affected. Find what you can as steps 2 and 3 of **A uniqueness refusal** do (with `--tenant` for each app-tenant, since these are tenant records), keep those whose parent field's value in `data` (for `isParent`, the field `field update --id` names) is the `id` of an app-wide record of the referenced entity (`records list --app APP_ID --entity REFERENCED_ENTITY_ID --app-wide --env ENV_ID --json`, the entity being the field's `referencesEntity` in `model show`), show the user those as the ones found so far, not necessarily all of them, and ask which remedy to use for each; change only the records the user names: give each a parent from its own app-tenant in that same field (the user picks the parent), delete it (its records beneath it through unmanaged entities then follow the deleted-parent case in the managed paragraph above), or, for the `isParent` case only, make the entity managed with `entity update --managed`, which changes who can read the entity's existing tenant records, and the records beneath them through unmanaged entities: each record's own shares then decide who reaches it and those beneath it through shares, in place of the old parent's (roles' read access follows the parent field, not whether the entity is managed, so it is unchanged; deleting or restoring one of the entity's own records then takes manage access, not edit, and sharing one takes manage access to that record), and a record with no shares of its own first gets a view share for everyone in its app-tenant and a manage share for its creator (if the creator has an undeleted account and is a member of that app-tenant or a client-level member). Then run the command again. If it is refused again, affected records remain: ones the user chose to leave, ones you can't see, or ones whose parent is a deleted app-wide record, which no listing marks. Tell the user that, and that the entity can stay as it is; for the `isParent` case, making the entity managed clears it whatever the cause |

`CLI_ERROR` with a message such as `Unknown field type` is a bad flag value: fix it and run the command again.

### A uniqueness refusal

`constraint add` has no `--env` and acts in the application's default environment. The error names the duplicate records only when they are in that environment and the user can read them. Adding a second or later constraint checks only that constraint's fields; the entity's other constraints are unaffected.

1. Records named: ask the user which of them to change or remove, do it, then run `constraint add` again. The message can end "records in another environment of this application also share values" (do step 2 after this one) or "records in other app-tenants also share values" (step 3 for those).
2. The message says records are in another environment of this application, alone or after named ones: that can be the environment `multipaas.json` pins. Listing by environment needs CLI 0.13.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as at the top. Take each `ENV_ID` from `multipaas envs list --app APP_ID --json`. Find the records with `multipaas records list --app APP_ID --entity ENTITY_ID --app-wide --env ENV_ID --json`, and for each app-tenant of that environment (`multipaas tenants list --app APP_ID --env ENV_ID --json`) with `--tenant APP_TENANT_ID` in place of `--app-wide --env ENV_ID`. Ask the user which to change or remove, do it, then run `constraint add` again.
3. The message is only "existing records share values for the constrained fields", or says "in other app-tenants", or `UNAUTHORIZED` stops the listing, or step 2 finds none of the duplicates: the user can't read those records, and the bare message can also mean they can read app-tenant records but not app-wide ones. Tell them to ask someone who can to clear the duplicates, then run `constraint add` again.
