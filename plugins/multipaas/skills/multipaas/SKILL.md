# MultiPaaS CLI

`multipaas` is the MultiPaaS command line. It acts as the signed-in developer, with exactly the permissions they have in the MultiPaaS web app.

Always pass `--json`. With it, every command prints exactly one JSON document on stdout. Always read the exit code.

A value from the user or their data, such as a name, a path, an enum value, a default or a URL, never goes into a command bare or inside double quotes, where the shell would run a `$(…)` or a backtick in it. Put it in single quotes, as in `multipaas apps create --name 'NAME' --json`, and write each `'` in the value as `'\''`. Keep a leading `~/` of a path on disk outside the quotes, as in `--dir ~/'old app/export'`; a name, such as an import file part's `--name`, stays wholly inside them even when it starts with `~/`. A command other than a single `multipaas` call, such as one that runs `find` or `shasum`, sets each value once as a single-quoted variable and reads it back as `"${X:?}"`, as in `A='FILE' B='OTHER FILE' && shasum -a 256 -- "${A:?}" "${B:?}"`. Never name the variable `PATH`, `HOME` or another variable the shell uses. Ids the CLI printed go in as they are. A JSON object in single quotes, such as `--data '{...}'`, writes each `'` in it as `'\''` too.

## Install

Run `multipaas --version`. If the command is missing, ask the user to install it. Then:

```bash
brew install multipaas-apps/tap/multipaas
```

## Which MultiPaaS

The CLI talks to `https://api.multipaas.com` unless the environment variable `MULTIPAAS_API_URL` is set. The user sets it themselves, to the URL they were given. Never make one up, and don't set it unless the user tells you the value. A sign-in is kept per URL, so after the user changes it they sign in again.

## Which sign-in

A developer can keep one sign-in per profile, for example one per client they work for. The CLI uses the profile that `--profile` names, else the one the environment variable `MULTIPAAS_PROFILE` names, else the user's unnamed sign-in. The user chooses it for their shell, and you inherit it. Never set, change or unset `MULTIPAAS_PROFILE` yourself, and never pass `--profile` unless the user asks you to run a command as a profile they name. When you need to know which sign-in you are using, run `multipaas whoami --json`: its `"profile"` is the profile's name, or `null` for the unnamed sign-in.

Profiles need CLI 0.10.0 or later: on an older `multipaas --version`, `MULTIPAAS_PROFILE` is ignored and commands run as the unnamed sign-in, so check the version before relying on a profile, and see the `multipaas-build` skill for the upgrade.

If a command exits 2 with `NOT_SIGNED_IN`, its message gives the `login` command that signs in to the profile it ran as: for a named profile, `multipaas login --profile NAME`. Run that command with `--json` added, in the background as "Signing in" describes, then run the original command again, with the same `--profile` if it had one. If a command exits 1 with `NOT_FOUND` and its message ends with `(signed in with profile "NAME")` or `(no profile chosen: ...)`, the shell may be set to the wrong sign-in. Tell the user which profile it ran as, and don't switch profiles yourself.

The CLI keeps the developer's sign-in to itself. Never read, print or copy its stored credentials, and never call a MultiPaaS API with the developer's token. Use the CLI's commands. When none does what is needed, tell the user rather than working around it.

On `DUPLICATE_INVITATION`, the address has an open invitation with `kind` `email` to that app-tenant, an expired one included: when signed in as a person, run `tenants members` and show the user the roles of its `kind` `email` invitation for the address, ignoring any `kind` `import` one, and change them with `tenants invitation update` only if the user asks. If the address is now among `members`, tell the user the person is already a member. If `tenants members` doesn't list a `kind` `email` invitation for the address, it may be hidden from the user, or gone since this refusal: ask the user whether to run the probe, the same `tenants invite` they confirmed. It sends the email unless that app-tenant has a live open `kind` `email` invitation for the address, one with a live role or group, expired included, whether or not the user can see it, and only then is it refused with `DUPLICATE_INVITATION`; for any other refusal, follow that refusal's own branch in these rows. Run the probe once: after a second `DUPLICATE_INVITATION`, don't run it again, and tell the user someone who manages access there can resend or delete the invitation in the MultiPaaS web app. On `INVALID_EMAIL`, ask the user for the address again. On `INVITATION_NOT_SENT`, sending the email failed, so this invite created no invitation: tell the user, and run it again, as above, only when they ask. A deployer can also run `tenants members` and `tenants invitation update` in those app-tenants, and handles their refusals as here. Signed in as a person, on `NOT_FOUND` "no app-tenant … that you can reach", `--tenant` or `--app` is wrong, the app-tenant or its environment was deleted, or the user holds no role in that app-tenant: confirm the ids with the user. It needs CLI 1.12.0 or later: check `multipaas --version` first, and if it is older, ask the user to upgrade as under "Exit codes" |

## Signing in

`login` opens the user's browser and waits up to 5 minutes for them to approve "Allow MultiPaaS CLI?".

1. Run it in the background, because it blocks until the user approves.
2. Tell the user to approve in their browser. Show them the URL that `login` prints on stderr, in case no browser opened.
3. When it exits 0, carry on with what the user asked for.
4. If `login` itself exits 2 (`SIGN_IN_REFUSED` or `SIGN_IN_TIMEOUT`), the user declined or did not approve in time. Tell the user, and do not run `login` again unless they ask you to.

## Exit codes

| Exit | Meaning | What to do |
|---|---|---|
| 0 | Done | Use stdout |
| 1 | Refused or failed. stdout is `{"error": {"code": "CODE", "message": "MESSAGE"}}` | Tell the user the message and code. `REVOKE_FAILED` (from `logout`) means the user is signed out on this machine but the server did not confirm revoking the tokens: tell the user, and don't retry. `INVALID_API_URL` means `MULTIPAAS_API_URL` is set to a value the CLI refuses (it must be an `https` origin on an `api.` host): tell the user, and don't try other values. `INVALID_PROFILE` means `--profile` or `MULTIPAAS_PROFILE` names a profile the CLI refuses: tell the user, and don't try other names. `CLIENT_REQUIRED` (from `apps create`) means the user can reach more than one client: ask which, then run it again with `--client`. `ALREADY_MEMBER`, `DUPLICATE_INVITATION`, `INVALID_EMAIL` and `INVITATION_NOT_SENT` (from `tenants invite`) are covered in its row under "Commands". Any other code except `CLI_ERROR` is MultiPaaS refusing on purpose: don't retry the same command, unless its row allows it or the user says the cause is fixed. `CLI_ERROR` is a failure on this machine or the network (offline, a server error, a bad flag): fix the flag if that is the cause, otherwise tell the user and retry once they say the problem is resolved |
| 2 | Not signed in (`NOT_SIGNED_IN`), or `login` was declined or timed out (`SIGN_IN_REFUSED`, `SIGN_IN_TIMEOUT`) | For `NOT_SIGNED_IN`, sign in as the message says, adding `--json` (see "Which sign-in"), then run the original command again. For `SIGN_IN_REFUSED` or `SIGN_IN_TIMEOUT`, tell the user and stop: don't run `login` again on your own |
| 3 | This CLI is too old for MultiPaaS | Ask the user to run `brew update`, then, as a separate command, `brew upgrade multipaas`, then retry |
